1全景：这个项目到底在解决什么

一句话：给「有状态、能调工具、记得住用户」的聊天服务，提供一个可以直接上生产的骨架。 它不是 demo，所有「能跑起来」和「跑得稳」之间的差距，都在这个仓库里被显式处理过了。

接入层
FastAPI + slowapi + asgi-correlation-id — 路由、限流、请求 ID、CORS、统一异常。入口 app/main.py
会话与身份
JWT + SQLModel — 用户表 / 会话表；token 的 sub 先装 user_id 再装 session_id，两套依赖分别解析
Agent 编排
LangGraph StateGraph — chat → tool_call → chat 两节点环；AsyncPostgresSaver 存每一步状态
模型调用
LLMRegistry + LLMService — 预建多模型实例、tenacity 重试、环形降级、结构化输出
数据层
PostgreSQL 一个库装三样东西 — 业务表（user/session）、checkpoint 三表、mem0 的向量表 longterm_memory
缓存层
Redis — 只干两件事：mem0 检索结果缓存（60s TTL）、slowapi 跨进程限流计数
可观测
structlog + Prometheus + Langfuse + pyinstrument — 日志带 request_id、指标走 /metrics、trace 在 Langfuse、慢请求自动剖面
工程化
uv + Alembic + pre-commit + GitHub Actions + 多阶段 Docker — 锁版本、迁移、静态检查、构建发布

一次 POST /api/v1/chatbot/chat 真实走过的路

这条链路把大部分文件串起来了，理解它，剩下的文件基本能自动归位。

  1. 接入：CorrelationIdMiddleware 生成 request_id → MetricsMiddleware 开始计时 → LoggingContextMiddleware 解 JWT 把 session_id 塞进日志上下文。
  2. 限流：@limiter.limit(...) 命中，key 是客户端 IP，计数打到 Redis 的 LIMITS: 前缀。
  3. 鉴权：get_current_session 校验 token → 查 session 表 → 拿到 user_id / username。
  4. 请求校验：ChatRequest → Message 逐条检查长度、脚本标签、空字节。
  5. 命名（可选）：会话还叫空名时，UPDATE ... WHERE name='' 原子抢占，抢到的那个请求起后台任务让 nano 模型起标题。
  6. 进图前并发准备：asyncio.gather(graph.aget_state(...), memory_service.search(...)) —— 状态检查和长期记忆检索同时跑，省 200–500ms。
  7. 拼消息：load_system_prompt() 注入用户名、长期记忆、当前时间 → prepare_messages() 用 tiktoken 按 MAX_TOKENS 从尾部裁剪。
  8. 模型调用：LLMService.call() 整体 asyncio.wait_for(60s)；内部 tenacity 重试；失败就换注册表里下一个模型，环形转一圈。
  9. 图路由：模型返回 tool_calls 就去 tool_call 节点并发执行工具，否则回 END；每步状态由 checkpointer 落库。
  10. 落记忆：create_background_task(memory_service.add(...)) 后台跑，不挡响应；只把最后一条用户消息交给 mem0。
  11. 出站：__process_messages() 把 LangChain 消息转成 {role, content}，丢掉 tool 消息。
  12. 度量：耗时写进 http_request_duration_seconds，LLM 段单独记 llm_inference_duration_seconds。
先记住一个反直觉的事实

这个项目里 PostgreSQL 是单点，不只存业务数据。checkpointer 一旦连不上， create_graph() 会直接抛异常——代码里特意没做「降级为无 checkpointer」的兜底，因为那样会静默丢对话历史。 所以排障顺序永远是：先看 PG，再看 LLM，最后看别的。

3搭建路线：按中间件引入，10 步一次到位

顺序不是随便排的。原则只有一条：每一步只引入一个新外部依赖，且这一步结束时系统能独立验收。 这样任何一步出问题，你只需要怀疑「刚加的那一个东西」。

引入顺序与理由
阶段引入什么为什么必须是这个位置
0 骨架uv / Python 3.13后面每个依赖都靠它锁版本
1 地基配置 + 结构化日志配置导入即校验，日志是所有排障的眼睛——晚于任何服务都会让你盲调
2 存储PostgreSQL + Alembic三张业务表先立起来；checkpoint 与向量表后面才来，但都落这一个库
3 身份JWT会话是聊天的前置；没有 session_id 就没有 thread_id
4 模型LLM先能稳定调通一次模型，再去谈编排
5 编排LangGraph + checkpointer图需要 thread_id（来自 3）和模型（来自 4）
6 接口Chat API + SSE到这一步才第一次有端到端闭环
7 记忆mem0 + pgvector依赖 2 的库和 4 的 embedding，且是「锦上添花」，坏了不影响主链路
8 缓存/限流Redis纯性能与安全增强，前面没有它也能跑
9 可观测Prometheus / Langfuse / 剖面要先有东西可观测；顺序反了就是空转
10 交付Docker / CI / 评测最后固化，避免早期反复重建镜像
关于 Docker

本机没装 Docker 也完全可以走完 0–9 步：第 2 步用一个已有的 PostgreSQL（比如你那台阿里云，建独立库跑）， 第 8 步用一个已有 Redis 的非 0 号库。第 10 步的镜像构建可以最后再补。

6.1 三个决定接口形态的细节

  • agent 是模块级单例：agent = LangGraphAgent() 写在模块顶层，全进程共用编译好的图。别在路由里 new，否则每个请求都重建连接池。
  • 非流式返回整段历史：ChatResponse(messages=result) 里是「用户消息 + 助手回复」，前端直接整屏替换，不用自己拼。
  • 流式用 SSE，错误也走 SSE：data: {"content":"...","done":false}\n\n，最后一帧 done=true。 中途异常不换 HTTP 状态码（响应头早发出去了），而是把错误文本塞进最后一帧。
bash
TOKEN=$(curl -s -X POST localhost:8000/api/v1/auth/session \
  -H "Authorization: Bearer $USER_TOKEN" | python -c "import sys,json;print(json.load(sys.stdin)['token']['access_token'])")

curl -X POST localhost:8000/api/v1/chatbot/chat \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"messages":[{"role":"user","content":"你好"}]}'

curl -N -X POST localhost:8000/api/v1/chatbot/chat/stream \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"messages":[{"role":"user","content":"你好"}]}'
会话自动命名为什么值得做

用户不会给会话起名，列表页就会全是「新对话」。做法：第一条消息进来时， 用 UPDATE session SET name=? WHERE id=? AND name='' 原子抢占， 只有 rowcount==1 的那个请求去调模型；同时先写一个占位名（用户首句前 40 字）， 这样即使模型调用失败，列表里也有可读文字。多 worker 并发也不会重复调。

两件事必须自己确认

① DB 编号：别用 0 号库。如果同一台 Redis 上还跑着别的服务（比如 MaxKB），key 空间会混，KEYS * 和清库都会误伤。本项目默认 REDIS_DB=1。

A1RuntimeError: JWT_SECRET_KEY must be at least 32 characters 配置层在导入时校验。改 .env 即可；注意 alembic 也受影响，不是只有服务。设计如此

B 组 · 起来了但不对

#现象根因与修法状态
B1服务健康、/health 200，但注册报「表不存在」 容器不跑迁移。make docker-migrate。这是「看起来跑起来了」的头号陷阱。流程要求
B2配了 REDIS_HOST 却仍是 in_memory redis 原先在 optional extra 里，Docker 的 uv sync --frozen 不装 extra → REDIS_AVAILABLE=False → 静默回落。已把 redis 提为主依赖。已修
B3登录接口一直 422 它是 Form(...)，必须 application/x-www-form-urlencoded，不是 JSON。接口约定
B4用 user token 调 /chatbot/* 返回 404 chat 接口要 session token。get_current_session 拿 sub 去查 session 表，查不到就 404。两种 token 不能混。设计如此
B5chat 报 llm call timed out after 60s 没配 OPENAI_API_KEY 或网关不通。注意它把所有重试都吃在 60s 总预算里，所以是"超时"不是"401"。配置问题
B6换国产模型后模型名报错 / 不识别 注册表里是硬编码的 4 个 gpt-5.x，不读 DEFAULT_LLM_MODEL。要改 LLM_CONFIGS，并注意这些条目都带了 reasoning 参数，非 reasoning 模型要删掉。需改造
B7长期记忆一直空，日志无异常抛出 embedding 模型（text-embedding-3-small）在你接的网关上不存在。换模型；或被 search 的 try/except 吞了，只有 failed_to_get_relevant_memory 一条 error。配置问题
B8会话列表全是「新对话」 SESSION_NAMING_ENABLED 关了，或命名强行指定的 gpt-5.4-nano 不在注册表里。配置问题
B9流式接口报错时前端收到 200 却是乱码 SSE 里业务异常不走 HTTP 状态码，而是最后一帧 {"content":"错误信息","done":true}。前端要判 done。接口约定

C 组 · 能跑但有隐患

#隐患说明与建议
C1限流在多副本下失效 没配 Redis 时 slowapi 用进程内存。10/minute × 4 worker = 40/minute。这是安全项，优先修。
C2REDIS_DB=0 与其他服务撞车 MaxKB 之类默认也在 0 号库。本项目已默认 1；如果你自己的 .env 还写着 0，要改。
C3database.py 的 async 方法内部是同步阻塞 with Session(engine) 是同步 IO，跑在事件循环里。低并发无感，高并发会拖慢所有请求。真上量要换 asyncpg + AsyncSession。
C4MAX_TOKENS 同时当输入裁剪上限和输出上限 prepare_messages 用 2000 裁历史，registry 也用 2000 限输出。长上下文场景应拆成 MAX_INPUT_TOKENS / MAX_OUTPUT_TOKENS。
C5单条消息 3000 字硬上限 schemas/chat.py 的 max_length=3000。要传长文档得改这里，同时考虑裁剪策略。
C6build-docker.sh 传了一堆没人接的 build-arg --build-arg OPENAI_API_KEY=... 但 Dockerfile 没有对应 ARG：既不生效，还可能留在构建元数据里。建议删掉这些参数。
C7模型单例 + 状态可变 llm_service 是全局单例，默认路径换模型会改 self._current_model_index。多 worker 各自独立没问题，但同进程内一旦降级过，后续请求都会用降级后的模型（直到下次切换）。
C8services/__init__.py 没导出 memory_service 容易写成 from app.services import memory_service 然后 ImportError。直接从 app.services.memory 导入。
C9模板残留：thread 表、orders_processed 指标 都没人用。删表要配套迁移，删指标直接删即可。
C10测试目录不存在 pyproject 配了 pytest，CI 里没有测试步骤。要加就在 tests/ 写，然后补一条 CI step。
