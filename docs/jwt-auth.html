1为什么「登录一次就记住」这么难

你在本机 make dev 跑起来，注册、登录、进聊天页，一切正常。 第二天把服务丢到一台带负载均衡的机器上、开了两个进程 —— 用户开始随机掉线： 刷新一下还在，再点一下发消息就 401。日志里干干净净，什么错都没有。

你以为发生的实际发生的
登录之后，服务端「记住我是谁了」它只是在自己进程的内存里记了一张表
换台机器、换个进程，它也认识我另一个进程的那张表是空的，谁也不认识你
刷新页面居然还在因为浏览器把那张表的编号带回来了，而它碰巧还落在原来的进程上

根子在一句话：HTTP 的每个请求都是一次陌生敲门。协议本身不记得你上过门。 服务端想认人，只有两条路——翻本子，或者验身份证。

路线做法代价
共享本子
Session		 登录状态存进 Redis，所有进程查同一本账，浏览器只揣一个编号 每个请求多一次网络 IO；Redis 一挂，全站掉线
自带身份证
JWT		 把身份和到期时间签进令牌，各进程用同一个密钥自己验，谁都不用查账 令牌发出去就收不回；密钥一泄漏，等于全站失守
fly-agent 选的是第二条

因为它后面要接 Agent、要能多实例横向扩、还要给移动端用。让每个请求都去查一次共享状态，等于给主链路加了一个必挂的依赖。

一句话带走「记住你」的本质只有一个选择：状态放服务端，还是签在凭证里。

2本质：一枚令牌的三段旅程

先看全貌。整件事只有四个动作，中间那两次「携带」是浏览器替你干的，你只写两头。

阶段谁来做具体动作做错会怎样
签发服务端把「谁 + 什么时候过期」写成一段 JSON，用密钥算个签名贴在后面密钥太弱或写死在代码里 → 谁都能伪造一张
携带客户端放进请求头 Authorization: Bearer <token>放错位置、丢了 Bearer 前缀 → 一律 401
验签服务端用同一个密钥重算签名，再检查 exp 有没有过期只解码不验签 → 等于门锁挂门上没锁
核心认知：它不是「查」出你是谁，是「算」出你是谁

服务端手里没有你的登录记录，只有一把密钥。每次请求它把签名重算一遍，对得上就信你——这就是「无状态」四个字的全部含义。

这个设计换来的是：加机器不用同步状态、跨域跨端都能用、一次请求零次 IO。 代价藏在第五章：算出来的东西你改不回去。令牌一旦发出去，在到期之前它就一直有效，你没有任何办法提前作废它。

一句话带走服务端不查账只验签——省下的那次 IO，换来的是撤不回的令牌。

3差异：四个名字，三层楼

面试最爱问「JWT 和 Session 有什么区别」「为什么不用 OAuth 2.0」。 这两个问题的坑在于——它们压根不在同一个楼层，硬比就是错的。

七个维度摊开看

维度Cookie + SessionJWTOAuth 2.0
状态存哪服务端（内存 / Redis），Cookie 只揣一个编号客户端，身份信息全在令牌里协议层，不规定令牌格式
每次请求成本查一次会话存储，一次网络 IO本地验签，零 IO看实现，常配 JWT
水平扩展要共享存储或粘性会话，否则随机掉线各节点共享密钥即可，加机器就扩—
主动失效删掉会话立即生效，能一键踢人到期前撤不掉，只能黑名单 + 短有效期有专门的吊销端点
单请求体积几十字节几百字节到 1–2 KB—
主要攻击面CSRF：别的站点借你的 Cookie 发请求存浏览器本地存储挨 XSS；存 Cookie 挨 CSRF跳转劫持、令牌泄漏、权限范围给太宽
典型场景单体后台、要求立刻踢下线多服务 / 跨域 / 无状态 API / 移动端第三方授权、单点登录
选型口诀

要立刻踢人 → Session；要多节点不查库 → JWT；要让第三方访问用户资源 → 才轮到 OAuth 2.0。
反过来说，JWT 的账也在这儿：撤不回来。所谓「登出」，在 JWT 体系里不是删令牌，而是让它早点过期——第六章展开。

四个一听就露怯的说法

常见说法为什么不对
「JWT 是加密的，别人看不到内容」只是 Base64URL 编码，不是加密。把中间那段贴进任何解码器，明文立刻出来
「用了 JWT 就不需要 Cookie 了」Cookie 是运输工具，JWT 是货。你完全可以把 JWT 装进 Cookie 送
「OAuth 2.0 是登录协议」它是授权框架，回答的是「这个应用能不能代表用户做事」；认证是 OIDC 补的身份层
「JWT 比 Session 安全」安全模型不同，不是强弱之分。Session 怕 CSRF，JWT 怕 XSS 和撤不回
一句话带走OAuth 2.0 管怎么发，JWT 管长什么样，Cookie 管怎么带——三者不打架。

4要素：长什么样、放什么、多久过期

一个 JWT 就是把三段字符串用两个点拼起来。打开你之后签发的那一枚，它长得这样：

token 的结构
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9 . eyJzdWIiOiI0MiIsImV4cCI6MTc2MjExMjAwMH0 . 3Xv9kQ...
└────────── header ──────────┘   └────────── payload ──────────┘   └─ signature ─┘
部分装什么铁律
header{"alg":"HS256","typ":"JWT"}算法名。验签时白名单必须写死，永远不接受请求方自己声明的 alg
payload标准字段 + 少量自定义字段，明文可见只放「身份标识」，绝不放手机号、身份证、密码、完整权限列表
signature用密钥对前两段算出的签名只保证「没被改过」，不保证「没被看过」

亲眼看一眼 payload 是明文的

python · 解码任意 JWT 的中间段
import base64, json

payload = token.split(".")[1]          # 中间那段
payload += "=" * (-len(payload) % 4)   # 补齐 Base64 的填充
print(json.loads(base64.urlsafe_b64decode(payload)))
# {'sub': '42', 'typ': 'access', 'iat': 1762110000, 'exp': 1762111800, 'jti': '9f3c...'}

不需要密钥就能解。这就是为什么「别放敏感信息」不是一句客套话。

字段怎么填

字段含义你这门课里怎么填
sub主体，这张令牌代表谁用户 id。仓库里装的是会话 id（thread_id），只是装的东西不同
exp过期时间戳必须填，且必须被校验。不填等于永久有效
iat签发时间填上，排查「这枚令牌哪来的」时有用
nbf生效时间一般不用；要用就留 30–60 秒时钟误差余量
jti令牌唯一编号一定要填，它是不允许重复消费和做吊销的唯一抓手
typ令牌类型（自定义）区分 access 与 refresh，防止拿续期令牌直接当访问令牌用
数值边界，别凭感觉设

访问令牌 30 min（半小时，够一次连续操作就好）；续期令牌 14 天；时钟误差容忍 30–60 秒； 密钥长度至少 32 个字符，用 secrets.token_urlsafe(32) 生成，不进代码、不进 Git。

仓库里当前 JWT_ACCESS_TOKEN_EXPIRE_DAYS=30——一个访问令牌活三十天，等于把「撤不回」这个缺点放大到极致。这一节会让你把它改成半小时。

算法怎么挑：单服务自己签自己验，HS256 够了，一把密钥两边用。 一旦出现「签发方不是验签方」（网关、多服务互信），就换 RS256 / ES256：私钥只留在签发方，验签方拿公钥。

一句话带走payload 是明信片不是保险箱——签名只保证没被改，不保证没人看。

2
密码只存哈希这一步做错，后面全白做
改 app/models/user.py依赖 bcrypt
python · app/models/user.py
import bcrypt


def hash_password(raw: str) -> str:
    return bcrypt.hashpw(raw.encode("utf-8"), bcrypt.gensalt()).decode("utf-8")


def verify_password(raw: str, hashed: str) -> bool:
    return bcrypt.checkpw(raw.encode("utf-8"), hashed.encode("utf-8"))
bcrypt 的隐形天花板

它只认前 72 个字节，超长密码会被静默截断。注册入口先拦一道长度上限，别让用户以为「密码越长越安全」。

Checkpoint

库里 hashed_password 以 $2b$ 开头；同一个密码注册两次，落库的两个哈希不一样（盐是随机的）。

3
签发：把身份算成一张签名纸三十行不到的核心
新建 app/utils/auth.py依赖 PyJWT
python · app/utils/auth.py
from datetime import UTC, datetime, timedelta
from uuid import uuid4

import jwt

from app.core.config import settings


def create_token(sub: str, ttl_min: int, typ: str = "access") -> str:
    now = datetime.now(UTC)
    payload = {
        "sub": sub,
        "typ": typ,
        "iat": now,
        "exp": now + timedelta(minutes=ttl_min),
        "jti": uuid4().hex,
    }
    return jwt.encode(payload, settings.JWT_SECRET_KEY, algorithm=settings.JWT_ALGORITHM)
时间要用带时区的 UTC

datetime.now(UTC)，不是 datetime.utcnow()。后者返回的是「没有时区的假 UTC」，一旦服务器时区不是 UTC，过期判断会整体偏移，且不报错。

Checkpoint

打印出来的令牌刚好被两个点分成三段；用上页那段解码脚本能读出你刚写的 sub 和 exp。

4
校验 + 守卫：把门锁上最容易写错的一段
追加 app/utils/auth.py追加 app/api/v1/auth.py
python · 校验：algorithms 必须是写死的白名单
def decode_token(token: str) -> dict:
    return jwt.decode(
        token,
        settings.JWT_SECRET_KEY,
        algorithms=[settings.JWT_ALGORITHM],   # 写死，不接受请求方指定
        options={"require": ["exp", "sub"]},
    )
python · 守卫：一个依赖，所有受保护接口共用
bearer = HTTPBearer(auto_error=False)


async def get_current_user(
    cred: HTTPAuthorizationCredentials | None = Depends(bearer),
    db: AsyncSession = Depends(get_db),
) -> User:
    if cred is None:
        raise HTTPException(401, "missing_token", headers={"WWW-Authenticate": "Bearer"})
    try:
        payload = decode_token(cred.credentials)
    except jwt.ExpiredSignatureError:
        raise HTTPException(401, "token_expired", headers={"WWW-Authenticate": "Bearer"})
    except jwt.InvalidTokenError:
        raise HTTPException(401, "invalid_token", headers={"WWW-Authenticate": "Bearer"})

    user = await db.get(User, int(payload["sub"]))
    if user is None:
        raise HTTPException(401, "user_not_found")
    return user
401 和 403 别混着用

「你没带凭证 / 凭证不对」是 401，还要带上 WWW-Authenticate 头； 「你是谁我知道了，但你没这个权限」才是 403。混用会让前端做不出正确的跳转逻辑。

Checkpoint

访问受保护接口时：不带令牌 → 401 且响应头里有 WWW-Authenticate；令牌末尾多打一个 x → 也是 401，但错误码是 invalid_token。两者必须能区分开。

5
三个端点：登录、我是谁、续期把四块代码串成一条路
改 app/api/v1/auth.py新增 3 个路由
python · app/api/v1/auth.py
@router.post("/auth/login")
async def login(body: LoginIn, db: AsyncSession = Depends(get_db)) -> TokenOut:
    user = await db.scalar(select(User).where(User.email == body.email))
    if user is None or not verify_password(body.password, user.hashed_password):
        raise HTTPException(401, "bad_credentials")          # 不区分「没这人」和「密码错」
    return TokenOut(
        access_token=create_token(str(user.id), settings.JWT_ACCESS_TTL_MIN),
        refresh_token=create_token(str(user.id), 60 * 24 * settings.JWT_REFRESH_TTL_DAYS, "refresh"),
        token_type="bearer",
    )


@router.get("/auth/me")
async def me(user: User = Depends(get_current_user)) -> UserOut:
    return UserOut(id=user.id, email=user.email, username=user.username)


@router.post("/auth/refresh")
async def refresh(body: RefreshIn, db: AsyncSession = Depends(get_db)) -> TokenOut:
    payload = decode_or_401(body.refresh_token)
    if payload.get("typ") != "refresh":
        raise HTTPException(401, "wrong_token_type")
    if await is_revoked(db, payload["jti"]):
        raise HTTPException(401, "refresh_revoked")
    return TokenOut(
        access_token=create_token(payload["sub"], settings.JWT_ACCESS_TTL_MIN),
        refresh_token=body.refresh_token,
        token_type="bearer",
    )
登录失败只说一句话

bad_credentials 一个错误码盖住两种情况。分开回「邮箱不存在」和「密码错误」，等于免费送人一个账号枚举接口。

全过的标志

四条全中，说明「签发 → 携带 → 验签 → 放行」这条链路第一次真正闭环。第 4 条最容易假通过——如果你的代码只解码不验签，它照样返回 200。

一句话带走认证就三行逻辑：发一张签了名的纸，收回来验一遍签名，验不过就 401。

6把活交给 AI：六条提示词

vibe coding 不是「说一句帮我写个登录」然后验收 AI 的想象力。 它是你把现场、约束、验收、输出四件事说死，让 AI 没有即兴发挥的空间。 提示词写得好不好，差别不在措辞礼貌，而在这四段有没有交代。

段你要说清什么漏了会怎样
交代现场栈是什么、配置在哪、改哪个文件、哪些文件不许动它给你一个凭空新建的项目结构，你贴不进去
说死约束算法白名单、时间库、错误码、能不能加新依赖它默认「能跑就行」：不校验算法、有效期给 30 天
写死验收三条可执行的命令 + 期望结果，最好带反例你只能靠「看着像对」来判断，漏洞要等上线才发现
规定输出只给哪几个文件的完整内容，不要 diff 片段它给你半截代码，你还得猜该插在第几行

下面六条对应前面六个步骤，改一下邮箱、路径就能直接用。

提示词 01 · 密钥与配置
现场：项目 fly-agent，FastAPI + uv 管理依赖，配置集中在 app/core/config.py，
      目前用 os.getenv 读取，没有 Pydantic Settings 类。

任务：加 JWT 相关的四个配置项。

约束：
1. .env.example 里加四项并附注释说明取值范围：JWT_SECRET_KEY / JWT_ALGORITHM
   / JWT_ACCESS_TTL_MIN / JWT_REFRESH_TTL_DAYS
2. config.py 里读取这四项，默认值分别是 "" / "HS256" / 30 / 14
3. 启动时校验：密钥为空、长度少于 32 字符、或等于 your-secret-key 这类占位串，
   直接抛 RuntimeError 并说明具体是哪一条不满足；测试环境跳过
4. 不引入任何新的第三方依赖

验收（三条都要过）：
- python -c "from app.core.config import settings; print(len(settings.JWT_SECRET_KEY))" 输出 >= 32
- 把 JWT_SECRET_KEY 改成空字符串再启动，进程必须报错退出，不许静默降级成默认值
- 把密钥改成 your-secret-key 再启动，同样必须报错

输出：只给 config.py 和 .env.example 改动后的完整相关片段，其他文件一个字都不要动。
提示词 02 · 密码哈希
现场：用户模型在 app/models/user.py，用 SQLModel，密码字段名是 hashed_password，
      已有 bcrypt 依赖。

任务：加哈希与校验两个函数。

约束：
1. 直接用 bcrypt 库调用，不要换成 passlib
2. 签名固定为 hash_password(raw: str) -> str 和 verify_password(raw: str, hashed: str) -> bool
3. 编码统一 utf-8
4. bcrypt 只认前 72 个字节，超长部分会被静默截断。请在这两个函数开头做字节长度判断，
   超限时抛 ValueError 并说明原因，不许静默放过
5. 不要修改 User 的字段定义

验收：
- 同一个密码连续哈希两次，两个结果必须不同（盐是随机的）
- verify_password 对正确密码返回 True，对差一个字符的密码返回 False
- 32 个中文字符的密码（96 字节）必须抛 ValueError，而不是悄悄通过

输出：只给 app/models/user.py 里新增的完整代码块。
提示词 03 · 签发
现场：配置项已就绪，密钥读 settings.JWT_SECRET_KEY，算法读 settings.JWT_ALGORITHM。

任务：新建 app/utils/auth.py，实现签发函数。

约束：
1. 签名固定为 create_token(sub: str, ttl_min: int, typ: str = "access") -> str
2. 用 PyJWT（import jwt），不要用 python-jose
3. payload 只放五个字段：sub / typ / iat / exp / jti，jti 用 uuid4().hex
4. 时间一律用 datetime.now(UTC)，不许出现 utcnow()
5. 算法从 settings 读，不许硬编码字符串 "HS256"
6. 这一步只写签发，不要顺手把校验函数也写了

验收：
- 返回的字符串刚好被两个点分成三段
- 把中间段做 Base64 解码后能读到 sub 和 exp，且 exp - iat 正好等于 ttl_min * 60 秒

输出：完整的 app/utils/auth.py。
提示词 04 · 校验与守卫
现场：app/utils/auth.py 里已有 create_token，app/api/v1/auth.py 里已有 router。

任务：追加 decode_token 函数和 get_current_user 依赖。

硬约束（这几条一个字都不许改）：
1. jwt.decode 的 algorithms 参数必须是 [settings.JWT_ALGORITHM] 这个列表字面量，
   绝对不许从令牌 header 里读 alg，也不许写成 None 或省略
2. options 里必须 require ["exp", "sub"]
3. 令牌缺失 / 已过期 / 签名不匹配，全部返回 401，并在响应头带 WWW-Authenticate: Bearer，
   错误码分别是 missing_token / token_expired / invalid_token
4. 不许用 403 代替 401
5. decode 失败时不许把原始异常字符串回给客户端

验收（三条都要能过）：
- 不带令牌访问受保护接口：401 + missing_token + 响应头有 WWW-Authenticate
- 令牌尾部多打一个字符：401 + invalid_token
- 手工把 exp 改成过去的时间再签一枚：401 + token_expired

输出：两个文件各自的完整改动，注明加在哪个函数的后面。
提示词 05 · 三个端点
现场：app/api/v1/auth.py 里已有 get_current_user 依赖和 create_token。

任务：实现三个端点。

1. POST /auth/login：收邮箱 + 密码，成功返回 access_token / refresh_token / token_type
2. GET  /auth/me：依赖 get_current_user，返回 id / email / username
3. POST /auth/refresh：拿 refresh_token 换一枚新的 access_token

约束：
- 登录失败统一返回 401 bad_credentials，不许区分「用户不存在」和「密码错误」
- refresh 端点必须先校验 payload 里 typ == "refresh"，否则直接拒绝

- 这一步不要建新表、不要写数据库迁移

验收：
- 登录能拿到两枚令牌，解码后 typ 一个 access 一个 refresh
- 把 refresh_token 当访问令牌去打 /auth/me，必须返回 401

三条最容易踩的反模式

① 一句话需求。「帮我用 FastAPI 写个 JWT 登录」——它一定给你一个能跑但不能上线的 demo：有效期三十天、算法不校验、密码不哈希。它能跑，只是因为它没考虑有人在攻击。

② 一次要五个文件。要得越多，它越容易编出你项目里根本不存在的函数名。一步一个文件，是最省时间的做法。

③ 不说验收。没有验收标准，你就只能靠「看着像对」判断，而安全类的错，看着永远是对的。

它给错了的时候，用这三句话追问

「这段代码在令牌被篡改的情况下会返回什么？给我一条能复现的 curl。」

「只改 app/utils/auth.py，其他文件不要动，把上一次顺手改的地方退回去。」

「把你刚才的改动列成清单：哪个文件、动了哪几行、为什么动。」

一句话带走提示词不是许愿，是把验收标准提前写成合同——标准越硬，返工越少。

7收口：软肋怎么补，坑怎么绕

软肋：令牌发出去，就收不回来了

用户点了「退出登录」，你除了把浏览器里那份删掉，什么也做不了——那枚令牌在到期前依然能打开你的接口。三条解法：

解法做法代价
缩短有效期访问令牌只活 30 min，过期自然失效体验差，用户频繁被弹回登录页
双令牌
本课采用		访问令牌短、续期令牌长；续期令牌存库，退出就把它标成已吊销多一个端点、多一张表
黑名单把 jti 塞进 Redis，到期自动清掉每次请求又得查一次，等于把省下的 IO 还回去

双令牌的关键只有一句：真正的撤销能力，落在数据库里那张秒级可查的小表上。访问令牌不查库，续期令牌才查库——高频的事保持无状态，低频的事走状态。

python · 续期令牌表，只记四列够用
class RefreshToken(BaseModel, table=True):
    id: int | None = Field(default=None, primary_key=True)
    jti: str = Field(unique=True, index=True)   # 对应令牌里的 jti
    user_id: int = Field(index=True)
    revoked: bool = Field(default=False)

对照实验：亲手把门打开一次

下面这段不需要密钥，就能伪造一张「合法」令牌。用它打你的 /auth/me，看返回什么。

python · 伪造 alg=none 的令牌
import base64, json

def b64(obj: dict) -> str:
    raw = json.dumps(obj, separators=(",", ":")).encode()
    return base64.urlsafe_b64encode(raw).rstrip(b"=").decode()

forged = b64({"alg": "none", "typ": "JWT"}) + "." + b64({"sub": "1", "exp": 4102444800}) + "."
print(forged)
如果它返回了 200，你的门就是开着的

说明验签这一步写成了「跟着令牌里声明的算法走」。攻击者声明 alg: none，服务端就不验签直接放行。 正确的写法只有一个：algorithms 参数写死成你自己的算法，绝不从令牌里读。

七条避坑清单

#坑正确做法
1algorithms 跟着请求走 / 不传写死白名单，写成常量，写进评审清单
2密钥写在代码里或提交进 Git只走环境变量；启动时校验长度和占位串
3往 payload 里塞敏感信息只放 id 这类标识，其余要用时现查库
4前端把令牌存进浏览器本地存储任何脚本都能读走。放内存 + 续期令牌走 HttpOnly Cookie
5401 和 403 混用凭证问题 401，权限问题 403，别让前端猜
6用 utcnow() 算过期用带时区的 datetime.now(UTC)
7刷新端点不校验 typ拿访问令牌也能换新令牌，等于给短有效期开了后门

考点速查

P0 必会三段结构与各自职责；为什么 payload 不能放敏感信息；服务端验签到底验了什么。

P1 常问有状态与无状态怎么取舍；登出为什么不能靠删令牌；访问令牌 + 续期令牌的完整流程。

P2 加分alg:none 与 kid 注入；公钥轮换怎么做到不停服；OAuth 2.0 与 OIDC 各管哪一半。

走到这里，fly-agent 的「认人」这一段就通了。下一步接 LangGraph 的时候，get_current_user 会变成你所有会话的入口—— 用户 id 从这一刻起有了出处，长期记忆才能按人分开存。

一句话带走JWT 不是更安全的 Session，是拿「撤销权」换「扩展性」的一笔交易。
