1市面全景：五派，不是一个榜单

搜「agent memory framework」会出来几十个名字，但它们解决的不是同一件事。看清楚分派，比看任何一个功能对比表都有用—— 因为派别决定了它的数据模型，而数据模型决定了你能问出什么问题、以及迁移有多贵。

派别核心赌注代表它擅长的提问
① 抽取式记忆层
Extracted facts		 把对话交给模型，抽出「一条一句的事实」，向量化存起来，按语义召回 mem0、Memobase、LangMem、LlamaIndex Memory 「这个人偏好什么」
② 时序知识图谱
Temporal KG		 事实带有效期，过期不删只失效；关系可多跳 Graphiti、Zep Cloud、Cognee、A-MEM 「上周他还是这个偏好么」「他和那个项目什么关系」
③ 记忆操作系统
Memory OS		 像操作系统管内存一样，让 agent 自己编辑、分页自己的记忆 Letta（原 MemGPT）、MemOS、Honcho 「长期自主运行，自己决定记什么」
④ 托管记忆服务
Managed		 把抽取、存储、召回、治理打包成 API，按量计费 Bedrock AgentCore Memory、Vertex AI Memory Bank、Cloudflare Agent Memory、Mem0 Platform、supermemory 「我不想运维向量库和抽取管线」
⑤ 文件式记忆
File / MCP		 一份人可读的文件就是一个记忆库，靠全文注入或 MCP 工具读写 CLAUDE.md / MEMORY.md 模式、Basic Memory、OMEGA 「我要能打开它、改它、审它」
先说一句容易搞混的

向量数据库不是记忆框架。Pinecone、Qdrant、Chroma、pgvector 是存储底座；记忆框架是搭在它们上面的「写入—抽取—召回—失效」生命周期。 有人跟你说「我们用 Pinecone 做 agent 记忆」，他的意思是「我们有一堆向量但没人在管它」。

四个死路，别把工期建在上面

Zep Community Edition（getzep/zep）：2025 年 4 月起弃用，开源路线改由 Graphiti 承接，自托管版不再更新。

Motorhead（getmetal/motorhead）：2023 年 12 月起停止维护。

Memary、Memoripy：作者已不再维护，代码能跑但没有安全更新，也没有人回 issue。

这四条的共同点：文档还挂在搜索结果第一页，README 也还写得挺像样。判断一个记忆框架能不能用，先看最近三次提交的日期，别看你手上那篇 2024 年的教程。

一句话带走先选派再选库：派别决定数据模型，数据模型决定你以后能不能换。

2逐个拆解：十个方案，各自的代价

下面这十个覆盖了绝大部分真实选择。每个只说四件事：它怎么工作、好在哪、代价在哪、什么时候该选它。 最后一项比前两项重要——选型里最没用的话是「功能很全」。

01mem0Apache 2.0
抽取式记忆层的默认答案。给一段对话，还你几条事实；下次按语义取回。
好在哪框架无关，几行接进任意栈；自带「增 / 改 / 删 / 不动」的冲突消解；向量后端可选 pgvector，不用新引入一套基础设施
代价抽取要过模型，写入有延迟和成本；抽取会错，且错得静默；精确字段（订单号、日期）召回不稳
什么时候选它多用户产品要「认识这个人」，团队不想自己写抽取管线。这也是本项目的选择。
02GraphitiApache 2.0
双时序知识图谱：每条边都记「什么时候为真」和「什么时候被写进来」。
好在哪能回答「当时是什么」；新事实来了把旧边标失效而不是删除；多跳关系（人 → 公司 → 项目）一次查完
代价要 Neo4j 或 FalkorDB；建图要过模型，入图成本是向量方案的数倍；图谱结构设计错了，返工比重写还贵
什么时候选它事实会变、且必须能追溯：合同、工单、客户档案、诊疗记录。答错一条失效事实的代价高于全部构建成本时。
03LettaApache 2.0
把上下文窗口当虚拟内存管：核心记忆常驻、归档记忆按需调页、agent 用工具自己改。
好在哪记忆编辑是 agent 的显式动作，每一步都能审计；跑几十天的长任务不会把上下文撑爆；分层思路清楚，是理解记忆分层的现成范本
代价agent 要跑在它的运行时里，这是最重的一种锁定；每次记忆操作都是一次模型调用，延迟和成本都高
什么时候选它长期自主运行的 agent，记忆本身就是它的行为。做产品接入层时别选它——你会为了一个记忆功能换掉整个运行时。
04CogneeApache 2.0
一条 ECL 流水线（抽取 → 建图 → 载入）把任意文档变成可查询的图 + 向量。
好在哪既能当「记忆」也能当「知识库」，两类需求一套 API；单 Postgres 就能起步，不用先上 Neo4j；有 LangGraph 集成
代价建图慢、可调试性差；抽象层多，出问题时要一路往下翻；open core，部分能力在企业版
什么时候选它既有「用户记忆」又有「文档知识」的需求，想用一套东西覆盖。纯记忆场景用它属于杀鸡用牛刀。
05LangGraph 自带开源
短期记忆 = 检查点（thread 状态）；长期记忆 = 你自己按 namespace 分区的 Store。
好在哪不用多一个依赖；schema、存储、检索逻辑全在你手里；和图的执行天然对齐，断点续跑开箱可用
代价抽取质量、去重、失效策略全要自己写；Store 只提供 KV + 语义检索，不提供生命周期
什么时候选它已经在 LangGraph 上，且记忆需求简单到「按 user 存几条事实」。再复杂就该上专门的库了。
06LangMem开源
LangChain 官方给的记忆原语：语义、情景、程序性三类，配抽取与更新工具。
好在哪和 LangGraph 同一个世界观，迁移成本最低；三类记忆的划分比大多数库清楚
代价出了 LangChain 生态就没什么用；生态小、示例少，遇到坑只能读源码；版本演进快
什么时候选它团队已经全押 LangChain，且愿意跟着它的版本走。
07Bedrock AgentCore Memory专有
AWS 把短期事件与长期记忆拆成两个原语，长期侧用可配置策略（摘要 / 偏好 / 事实）生成。
好在哪不用运维向量库；和 IAM、VPC、GovCloud 一套权限打通；2026 年已 GA，政企合规路径最顺
代价记忆锁在 AWS 里，迁移等于重建；检索管线不透明，调不了细节；按操作计费，量大会肉疼
什么时候选它已经在 AWS 上、有合规要求、且不打算自己调检索策略。政务云场景经常是这一条。
08Vertex AI Memory Bank专有
GCP 的长期记忆服务，按用户 scope 生成与合并记忆，跟着 Agent Engine 会话走。
好在哪会话与长期记忆在同一个产品里，衔接干净；和 ADK / Gemini 的长上下文配合得好
代价绑 GCP；记忆按事件单独计费；同样调不了抽取策略
什么时候选它Vertex 上的对话型 agent，且团队不想碰向量库。
09Memobase / Honcho开源
不做通用记忆，只做「用户画像」：这个人的偏好、习惯、长期状态。
好在哪颗粒度就是产品最常要的那一层，接上就有「记得我」的体感；比通用库更容易调准
代价只覆盖画像，会话续接、事实追溯都不管；社区小，出问题靠自己
什么时候选它需求就只是个性化，别的层你已经有了。
10Basic Memory / MEMORY.md开源
记忆就是一堆 markdown：人写得进去、改得动、能进 Git，agent 通过 MCP 或全文注入读。
好在哪零依赖、完全可审计、离线可用；写歪了一眼能看见，当场能改——这是所有自动抽取方案都给不了的
代价没有检索（靠全文塞提示）；没有隔离键；条数一多就变成第二份撑爆的上下文
什么时候选它单人自用、团队共享约定、或者任何「要人审一遍才敢生效」的记忆。别拿它做多租户。
一个反直觉的观察

这十家里，只有让 agent 自己决定记什么的方案（Letta、MemOS）会在生产里遇到「记忆越记越乱」， 而自动抽取式（mem0、Memobase）遇到的是「记错了还删不掉」。两类失败模式完全不同： 前者需要「遗忘策略」，后者需要「写入约束」。选型时先想清楚你能维护哪一种。

一句话带走每种记忆方案的真正代价，都落在「写错之后怎么修」上。

选型结论

1. 形态：抽取式向量层。它是唯一同时满足「跨会话」「按语义召回」「按 user_id 隔离」三项的形态。

2. 承担方：自建。开源库 + 自己的 PostgreSQL（pgvector），不引托管。

3. 具体到库：mem0。理由不是它最强，是它把「抽取 + 冲突消解 + 多后端」打包好了，且能落在已有的 PG 上。

4. 图谱留作二阶段：等到「事实会过期」成为真实投诉，再把那一层换成 Graphiti——两者的数据模型不冲突，可以并存。

最容易踩的坑

把「托管」当成「不用管」。托管省掉的是运维，不是治理：写入策略、隔离键、TTL、删除请求仍然要在你的代码里想清楚。云服务只是不让你装数据库。

用星数当生产就绪度。这个赛道的星数和维护状态经常背离——2024 年最火的那几个，有的 2025 年就停更了。看提交日期，不看 star。

注意 ⑤ 的位置：它画在 ④ 右边，但时间上与 ④ 并行——响应一返回，记忆写入就交给后台任务，用户不会为「记住这句话」多等一秒。 这条设计决定了整个链路的手感，也决定了失败处理方式：写入失败只记日志，不影响这一轮对话。

读写两条路径，分别是什么样

A
读：缓存 → 向量库 → 回填 三次判断，任何一次失败都不影响主流程
python · app/services/memory.py
async def search(self, user_id: str | None, query: str) -> str:
    if user_id is None:                      # 匿名会话直接跳过
        return ""
    key = cache_key("memory", str(user_id), query)
    cached = await cache_service.get(key)
    if cached is not None:                   # 60s 内同一个问题不查库
        return cached

    memory = await self._get_memory()
    results = await memory.search(user_id=str(user_id), query=query)
    result = "\n".join(f"* {r['memory']}" for r in results["results"])

    if result:                               # 只缓存成功且非空
        await cache_service.set(key, result)
    return result

外面还包了一层 try/except：异常时返回空串。记忆检索失败，退化成本轮没有记忆，而不是这一轮聊崩。 这个取舍很关键——记忆是增强项，不该成为可用性上的单点。

缓存后端跟着配置走：填了 REDIS_HOST 就是 Redis（多实例共享），没填就是进程内 TTLCache（单实例够用）。 两边行为一致：只缓存成功且非空的结果，错误永不入缓存。

B
写：只喂用户那一句 整个记忆质量的一半，在这一行上
python · app/services/memory.py
async def add(self, user_id: str | None, messages: list[BaseMessage]) -> None:
    if user_id is None:
        return

    user_text = latest_user_text(messages).strip()   # 只取最后一条用户消息
    if not user_text:
        return

    memory = await self._get_memory()
    await memory.add(
        [{"role": "user", "content": user_text}],
        user_id=str(user_id),
    )
为什么必须是「只有用户消息」

mem0 的抽取器会把一段对话里的多个角色拼起来理解。如果把助手回复也喂进去，助手提的建议就会被抽成「用户的偏好」—— 于是这个 agent 开始按自己上一轮的建议服务自己，越跑越偏。这一行不是优化，是防污染。

注入长什么样

检索回来的记忆不是当工具结果塞进去的，而是直接拼进系统提示的固定段落——每轮都在，模型不需要「想起来去查」。

app/core/prompts/system.md 片段
{user_context}

# What you know about the user
{long_term_memory}

# Current date and time
{current_date_and_time}

传进来之前，空值会被替换成一句兜底：relevant_memory or "No relevant memory found."。 这句兜底看着无害，其实是个小瑕疵——中文场景里突然出现一句英文，会轻微干扰模型的语气判断。第 6 章会把它列进清单。

一句话带走检查点管续接，mem0 管认人；读先查缓存，写只喂用户那句。

5七个取舍：为什么最后长这样

这一套不是「标准答案」，是七次「选了一边、放弃了另一边」。每一条都能被推翻，但你得知道推翻的是哪条。

#决策放弃了什么为什么这么选
1用 mem0，但不开它的图谱 「当时是什么」这类时间查询 记忆里全是偏好和背景，没有会过期的事实；开图要多一套 Neo4j，收益换不回运维成本。留作二阶段
2自建 MemoryService 包一层 少写一个类的省事 把「缓存、匿名跳过、只取用户消息、异常降级」四个策略收口在一处；将来换 mem0 或换库，只动这一层
3没用 LangGraph 的 Store / LangMem 框架原生的长期记忆 Store 只给 KV + 语义检索，抽取和冲突消解要自己写——这正是 mem0 已经做好的部分。而且 Store 换不来 pgvector 之外的收益
4记忆检索前面加 60s 缓存 「刚写的事实立刻能查到」的时效性 同一窗口里用户连着问相似问题很常见；60s 内复用结果，省掉一次向量查询。写入本身是异步的，本来就有秒级延迟，缓存不是主要瓶颈
5写入只取最后一条用户消息 多轮里逐步透露的信息（可能漏抽） 宁可漏，不可错。助手回复一进抽取器，就会出现「把建议记成偏好」的污染
6匿名会话（无 user_id）直接跳过记忆 匿名用户的个性化 没有隔离键的记忆等于给所有人共用一本笔记；宁可不记，也不要把所有匿名用户塞进同一个分区
7记忆文本作为图状态字段 检查点体积（每轮多存一份记忆快照） 节点里直接读 state.long_term_memory 拼提示，不用二次查库；代价是检查点里会残留历史记忆文本
第 2 条最值得学：边界层

很多项目把 mem0 直接调在路由里，于是「匿名怎么办、缓存放哪、异常了返回什么」这些策略散落在三个地方，改一次要翻五个文件。 包一层 MemoryService 的收益不在代码量，而在把外部依赖收口成内部接口——这一层也是你以后换框架时唯一要改的地方。

还有一处没进表，但值得单独说：检索与状态检查是并发的。 asyncio.gather(graph.aget_state(config), memory_service.search(...)) —— 这两件事互不依赖， 串着写就是白等一次往返（项目里标注这一处省下 200–500ms）。记忆系统的手感，往往就是由这类「顺手并发」决定的。

一句话带走好设计不是选了最强的方案，是把每个让步写在了明处。

6现状盘点：文档与代码的九处落差

这一章不是挑刺。记忆系统最危险的状态是「以为自己有」——文档写着有，代码里其实没有，或者反过来。 下面九条都是能对着文件核实的，写法是「文档说 / 代码是 / 影响」。

#落差实际是什么影响
1 缓存 key 的形状 文档写 memory:{user_id}:{sha256(query)[:16]}；代码是 cache_key("memory", user_id, query)，实际为 memory:{sha256(user_id:query)[:16]} 隔离是有效的（user_id 参与了哈希），但无法按用户批量失效缓存——删掉某人的记忆后，60s 内还可能返回旧值
2 空记忆的兜底句 relevant_memory or "No relevant memory found."，拼进中文系统提示的「你了解用户什么」段 中文场景里冒出一句英文，轻微干扰语气；更好的做法是空就不注入这一段
3 记忆文本进检查点 GraphState.long_term_memory 是被持久化的字段（schema 注释里写了），每轮覆写 检查点里会留下历史记忆文本快照 → 体积随轮数涨；且历史快照里有用户信息，删除会话时要注意
4 自定义抽取提示词没进文档 代码传了 custom_fact_extraction_prompt（prompts/memory_capture.md），配置表里一个字没提 这是本项目记忆质量的关键，却最容易在交接时丢掉——改默认提示词等于换了套系统
5 「排除助手回复」只在注释里 add() 只取最后一条用户消息，原因写在 docstring 里 后人「顺手」把整轮 messages 传进来，就会静默污染记忆，且不会有任何报错
6 抽取用的 LLM 没有独立端点 只有 embedder 支持 BASE_URL / API_KEY 覆写；mem0 的 llm 配置只给了模型名，跟随全局 OPENAI_BASE_URL 如果对话模型接的是第三方端点、那里没有 gpt-5-nano 这个名字，抽取会全部失败——而失败是静默的（只进日志）
7 事实永不过期 没有任何 TTL、失效或「截至」标记；只有新增与更新 半年前的目标会被当成现在的目标。这类错误用户很难纠正，因为他不会知道 agent 记着旧版本
8 检索没有重排、没有时间权重 直接取 mem0 返回的 top-k，未传 limit，也没有 recency 加权 新旧两条冲突事实同时命中时，靠相似度决定谁在前面，结果是随机的
9 删会话 ≠ 删记忆 clear_chat_history() 只清三张检查点表，不碰 pgvector 设计上正确（长期记忆要跨会话活），但产品文案必须说清，否则用户以为「删了会话就删干净了」
怎么用这份清单

第 1、2、6 条是真问题，改起来都很小；第 3、9 条是要写进产品文案和删除流程的边界； 第 4、5 条是交接风险，加一行注释就能挡住；第 7、8 条是能力缺口，属于下一阶段的事。 先分清这四类，再排优先级——不要把「能力缺口」和「一行能修的 bug」放在同一张待办上。

一句话带走记忆系统最危险的状态不是没做，是文档说有、代码里没有。

7改进路线：先修三处，再谈换框架

P0：这周就能改完

#改动怎么做
1空记忆不注入整段检索为空时，系统提示里直接省掉「你了解这个用户什么」这一节，而不是塞一句英文兜底
2缓存 key 带可读前缀改成 memory:{user_id}:{hash}，既能按用户批量失效，也让 redis-cli keys 一眼看得懂
3抽取模型补独立端点给 mem0 的 llm 也加上 base_url / api_key，别让它跟着对话模型的全局配置漂

P1：这个迭代排

#改动为什么
4事实带时间与来源写入时把「何时得知」写进 metadata；检索时优先近期，冲突时能判断谁新
5加一次重排取 10 条候选，用一次轻量调用或时间衰减重排到 3–5 条，比直接取 top-k 稳
6埋「记忆命中率」回答里用上了哪条记忆、用了几条，进 Langfuse trace。没有这个数，任何调优都是猜
7删除流程打通用户要求删除时，同时清缓存、清向量、清检查点，并留一条审计日志

P2：等它变成真需求

#改动触发条件
8引入 Graphiti 做时间层出现「你说的那是上个月的情况」这类投诉，且数量在涨
9多实例共享缓存从单实例扩到多实例，CACHE_TTL 开始各算各的
10记忆分级（重要 / 一般）记忆条数过万，检索噪声开始压过收益
四个「该换框架」的信号

① 开始需要「当时是什么」——同一事实有多个版本要并存 → 换时序图谱。

② 抽取错误率高到要人工兜底 → 换记忆 OS（让 agent 显式编辑）或改成人工确认流。

③ 单租户变成多租户、量级上一个数量级 → 该看托管服务了，自建的运维成本会反超。

④ 记忆已经是产品核心卖点、要有独立 SLA → 别再自己养，交给有专门团队的方案。

反过来说，没有这四个信号就别换。换记忆框架的代价不是改代码，是历史记忆的迁移—— 数据模型一变，旧记忆要么重抽一遍，要么丢弃重来。这是这个赛道最容易被低估的一笔成本。

考点速查

P0 必会五派的划分与各自的代表；为什么「向量数据库不是记忆框架」；长期记忆的隔离键为什么是 user_id。

P1 常问抽取式与图谱各自解决什么问题；托管服务的锁定点在哪（不是模型，是状态）；为什么写入要排除助手回复。

P2 加分Zep 开源版为什么停（引擎与平台拆开了）；双时序具体记哪两个时间；换 embedding 模型为什么要整表重建。

最后留一句判断标准：一个记忆方案好不好，不看它能记住多少，看它记错之后你多久能发现、多久能修好。 这句话对框架成立，对你自己的实现也成立。

一句话带走先修能修的三处，再等四个信号；换框架最贵的不是代码，是旧记忆。
