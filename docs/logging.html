让三个月后的你，还能查得动今天的日志

日志是唯一一个「写错了也不报错」的模块。接口照通，日志照样打， 直到真出事那天你打开文件，发现只有一句 error。 这一节把日志从「打印字符串」改成「可以查询的记录」，并让同一次请求的所有行自动带上同一个编号。

栈 structlog + asgi-correlation-id 你会跑通 一条请求的全链路日志 前置 中间件 / 依赖注入 / 环境变量

◎课程目标

01

02

03

05
学会审查 让 AI 扮演凌晨被叫醒的人，反过来挑自己日志的毛病。
不处理什么 — 日志采集与检索平台、轮转归档策略、告警规则。这些只需要知道「生产上日志会离开这台机器」，动手只到「本地那份 jsonl 能被查询」为止。

1日志写了三个月，第一次真出事

上线第三周，有人报「昨天下午发消息一直转圈」。你打开日志文件， 两千多行，长这样 —— 你从头翻到尾，一个有用的信息都没有。

logs · 真实的样子
[2026-11-02 15:41:07] ERROR: request failed
[2026-11-02 15:41:07] INFO: user login password=Passw0rd! email=a@b.com
[2026-11-02 15:41:09] ERROR: request failed
[2026-11-02 15:41:09] ERROR: retry
[2026-11-02 15:41:12] ERROR: request failed

两个失败同时发生。第一个是查不到：哪个用户？哪个会话？卡在调模型还是查数据库？调了多久？一个都答不上。 第二个是留太多：第二行里躺着用户明文密码 —— 这条日志本身的严重程度，比那次转圈高得多。

失败表现后果
查不到只有一句 error，没有编号、没有耗时、没有上下文出事时无法定位，只能靠复现，而线上的问题往往复现不了
留太多明文密码、Bearer 令牌、用户邮箱手机号合规事故。宕机还能修，泄漏没法收

根子是同一个：把日志当「打印」，而不是当「数据」。打印只要求人能看懂一眼；数据要求三个月后还能被检索、被聚合、被拿来算指标。

一句话带走日志的失败是静默的——它不报错，只在你最需要它的时候缺席。

2本质：一条日志要回答五个问题

先定标准，再谈写法。一条真正有用的日志，缺任何一个问题都算没写完。

#要回答的问题靠什么承载缺了会怎样
1是谁user_id只知道出事了，不知道谁出事，无法联系用户、无法回放
2哪一次请求request_id两千行日志混在一起，捞不出属于同一次的那几行
3哪一步event 名 + 模块/函数只知道失败了，不知道失败在调用模型还是写库
4发生了什么event + 关键参数只能靠猜，然后去读代码反推
5结果如何级别 + duration_ms + error不知道是慢还是错，更不知道慢到什么程度

这五个字段，不该由你手写

最直觉的做法是每次打日志都拼一遍 logger.info("failed", user_id=uid, request_id=rid)。 这条路一定会失败 —— 因为只要有一次忘了，那条日志就断了，而它往往恰好是你最需要的那条。 正确做法是让上下文自动跟着走：

核心认知：上下文跟着请求走，不跟着代码走

这两件事差别很大。跟着代码走，意味着每个函数都得把 user_id 当参数传下去，一路传到最底层； 跟着请求走，意味着只要在入口处绑一次，后面任何地方打日志它都在。Python 里做这件事的工具叫 contextvars， 它按协程隔离，所以并发一百个请求也不会串。

一句话带走别在每个调用点写 user_id——那正是最容易漏的地方。

3差异：print、logging、structlog 三代

日志工具的演进史，就是「字符串 → 结构化记录」的一步步退化掉文本的过程。搞清楚每一代丢掉了什么，你就不会再想用 print。

代工具它解决了什么它仍然做不到什么
一代print把东西打出来，仅此而已没有级别、不能关、不能过滤；生产环境还赖在 stdout，混进业务输出里
二代logging有了级别、有了 handler、能按环境切换输出仍是一整条字符串，想统计「登录失败几次」只能写正则
三代structlog事件名和字段分开，输出可被机器解析配置复杂，processor 顺序排错会静默失效

二代到三代的分水岭，不是好不好看，而是那句话还在不在字符串里。

为什么 f-string 是这行的头号禁区

python · 两种写法，后果完全不同
# 错的：所有信息都被焊死成一句话
logger.info(f"user {uid} failed to call model after {ms}ms")

# 对的：事件名固定，变量各归各位
logger.info("llm_call_failed", user_id=uid, duration_ms=ms)
问题f-string 写法造成的后果结构化写法
检索不到每个用户的 event 名都不一样，按事件名过滤全部落空事件名是主键，一条命令筛出所有同类
聚合不了「今天登录失败几次」得写正则，还得处理各种措辞jq 一句按 event 分组计数
算不了数耗时是字符串的一部分，取不出数字，算不了 P90duration_ms 是真数字，直接求和排序
可被伪造用户输入里带个换行，就能凭空造出一行日志字段值被序列化转义，伪造不了

级别怎么选

级别什么时候用例子
DEBUG排查时想看，但生产默认关掉拼好的 prompt、SQL 参数、重试次数
INFO业务里程碑。一次请求控制在 3–5 条，多了就是噪音登录成功、请求完成、后台任务入队
WARNING还能继续，但不对劲，需要人留意第一次重试、降级到备用模型、配置用了默认值
ERROR这次请求失败了，用户能感知到调模型超时、写库失败、外部接口 4xx/5xx
CRITICAL整个服务不能用了数据库连不上、密钥校验失败拒绝启动
ERROR 必须带堆栈，这是一条铁律

logger.error("call_failed", error=str(e)) 只留了一句话，没有现场。 换 logger.exception("call_failed") —— 它自动把当前异常栈附上。这一条最省事、也最常被漏。

一句话带走字符串进得去出不来——能被查询的才叫日志，其余都是打印。

4要素：怎么起名、填什么、不许留什么

事件名就是主键

规范只有一条：全小写、下划线分词、写「什么发生了」而不是写句子。 常见结构是「主体_动作_结果」，读起来像一条数据库记录，不像一句人话。

这样写为什么不行
user_login_succeeded ✓固定主键，能聚合、能报警、能写进检索语句
chat_request_failed ✓同理。名字里不带任何变量
f"user {uid} logged in"每个用户一个事件名，等于没有事件名
登录成功中文能打出来，但大多数检索语法按 ASCII 标识符匹配
error!! / xxx没有信息量，三个月后你自己也看不懂

五个必填字段

字段谁负责写说明
timestampprocessorISO 8601 带时区。不要用本地时间，跨时区排查会疯
levelprocessor由调用的方法决定，不用手填
event你唯一需要你亲自起名的字段，也是检索主键
request_id中间件串起一次请求的所有行，用户报障时你能直接要这个
user_id鉴权后绑定没登录的接口就没有，属正常

再加一个 duration_ms（真数字，不是字符串），你就同时拿到了「错没错」和「慢不慢」两个维度。

什么必须脱敏

字段处理
password / token / refresh_token整值替换成 ***，一个字符都不留
authorization / cookie / api_key / secret同上。请求头整条不要进日志
手机号 / 身份证 / 邮箱按需打码：保留前 3 后 4，中间 *
完整请求体（messages 数组、文件内容）不要进日志。需要时只记条数与总长度

脱敏最省事的做法不是「记得别打」，而是在输出前统一过一道处理器——人能忘，处理器不会。

用三个指标判断日志够不够用

指标目标工程化口径改哪里能影响它
可定位率≥ 90%随机抽 10 条 ERROR 日志，只凭内容能说出文件与函数，命中数 ÷ 10是否开 CallsiteParameterAdder、字段是否齐全
上下文覆盖率100%带 request_id 的行数 ÷ 总行数中间件注册顺序、绑定时机
敏感字段泄漏0 条全量日志里搜 password / token / authorization 的明文值出现次数脱敏处理器有没有挂在渲染前

第三条是质量底线，不为零就是事故，不是「待优化」。

数值边界，别凭感觉设

单条日志不超过 8 KB（超了采集器会截断，你还以为记全了）；嵌在日志里的对象不超过 1 KB； 本地文件保留 7–30 天；DEBUG 生产全关，高频 INFO 可按 1/100 采样。

一句话带走事件名是主键，字段是索引，脱敏是底线——三样缺一样，日志就白写。

5从 0 到 1：把日志接上

六步。前两步决定格式，中间三步决定上下文，最后一步决定你能不能真的查到东西。

1
先看清 print 到底丢了什么同一个事件，两种记法

Checkpoint

2
写出配置骨架一个开关决定彩色还是 JSON
改 app/core/logging.py读 settings.LOG_FORMAT
python · app/core/logging.py
import logging
import sys

import structlog
from asgi_correlation_id import correlation_id

from app.core.config import settings


def add_request_id(logger, method_name, event_dict):
    """把当前请求的编号补进每一条日志。"""
    rid = correlation_id.get()
    if rid:
        event_dict["request_id"] = rid
    return event_dict


def setup_logging() -> None:
    logging.basicConfig(format="%(message)s", level=logging.INFO, stream=sys.stdout)

    shared = [
        structlog.contextvars.merge_contextvars,   # 必须排第一
        structlog.processors.add_log_level,
        structlog.processors.TimeStamper(fmt="iso", utc=True),
        structlog.processors.StackInfoRenderer(),
        structlog.processors.format_exc_info,
        add_request_id,
        redact_sensitive,                          # 必须排在渲染之前
    ]

    renderer = (
        structlog.dev.ConsoleRenderer()
        if settings.LOG_FORMAT == "console"
        else structlog.processors.JSONRenderer()
    )

    structlog.configure(
        processors=[*shared, renderer],            # 渲染必须排最后
        wrapper_class=structlog.stdlib.BoundLogger,
        logger_factory=structlog.stdlib.LoggerFactory(),
        cache_logger_on_first_use=True,
    )


logger = structlog.get_logger()
processor 的顺序不是随便排的

merge_contextvars 排第一，是因为它要把上下文并进来，后面所有处理器才看得到； 渲染器排最后，是因为前面两步必须得到「还没变成字符串」的字段。 把渲染器往前挪一位，你就再也拿不到 request_id 和脱敏效果 —— 而且它不报错。

Checkpoint

开发环境打一条日志，终端是彩色的、一眼能读；把格式切成 production 重启，同一条日志变成一行合法 JSON，jq . 不报错。

让每个请求有个号一行注册，全站生效

from asgi_correlation_id import CorrelationIdMiddleware

中间件会读请求头里带的编号，没有就自己生成一个，并写回响应头。这样用户报障时，你只要一句话：把响应头里那个 X-Request-ID 发我。

Checkpoint

curl -i 任意接口，响应头里有 x-request-id；日志同一行里 request_id 与它完全一致。

4
鉴权之后，把人绑进上下文这一行决定日志有没有「谁」
改 app/api/v1/auth.py改 app/core/middleware.py
python · 鉴权成功后绑定
from structlog.contextvars import bind_contextvars, clear_contextvars


async def get_current_user(credentials=Depends(security)) -> User:
    ...
    bind_contextvars(user_id=user.id, session_id=session_id)
    return user
python · 每个请求开头清一次，防止上一个人的字段串过来
class ContextMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request, call_next):
        clear_contextvars()
        return await call_next(request)
为什么敢这么写

contextvars 是按协程隔离的。一百个请求并发，各自的 user_id 待在各自的上下文里， 互不可见。所以绑一次就够，不用层层传参，也不会串到别人身上。

Checkpoint

登录后打一次 /auth/me，日志里除 request_id 外多出 user_id 与 session_id； 不带令牌打同一个接口，这三样里只剩 request_id。

5
加一道脱敏人能忘，处理器不会
追加 app/core/logging.py挂在渲染之前
python · 关键词命中就抹掉值
SENSITIVE = {
    "password", "token", "access_token", "refresh_token",
    "authorization", "cookie", "secret", "api_key",
}


def redact_sensitive(logger, method_name, event_dict):
    for key in list(event_dict):
        if key.lower() in SENSITIVE:
            event_dict[key] = "***"
    return event_dict

想更稳一点，先 event_dict = dict(event_dict) 拷一份再改，别动调用方传进来的原始对象。

Checkpoint

故意用错密码登录一次，然后 grep 日志里那个密码明文 —— 搜不到；再用 jq 取 .password，值是 ***。

6
用一个编号，把一次请求捞出来这才是日志存在的意义
bash · 三条命令，由浅入深
# 1. 取出某次请求的全部日志
jq -c 'select(.request_id == "a3f9c1")' logs/development-2026-11-03.jsonl

# 2. 压成一条时间线
jq -r 'select(.request_id == "a3f9c1") | "\(.timestamp)  \(.event)"' \
  logs/development-2026-11-03.jsonl

# 3. 按事件聚合：今天哪类错最多（这一步文本日志做不到）
jq -r 'select(.level == "error") | .event' logs/development-2026-11-03.jsonl \
  | sort | uniq -c | sort -rn | head
#做什么期望
1开发环境打一条日志终端彩色可读，字段一目了然
2切到 production 重启一行合法 JSON，jq . 不报错
3带令牌打 /auth/me响应头有 x-request-id，日志里值一致，且带 user_id
4用错密码登录日志里密码是 ***，全库搜不到明文
5用刚才那个编号 jq 一遍拿到这次请求的完整时间线，能按时间读出经过
全过的标志

第 5 条能过，说明前面五步全部到位。第 5 条过不了，通常不是 jq 写错，而是中间某一步的 processor 顺序或中间件注册顺序有问题。

一句话带走日志配好那一刻毫无感觉，出事那一刻才见分晓。

6把活交给 AI：五条提示词

这一课的提示词和上一课不一样。认证写错了会 401，你当场知道； 日志写错了什么都不会发生，所以不能只说「帮我加个日志」—— 得先把契约写成硬约束，再让它写。五条里两条是审查类，那才是关键。

类提示词它替你解决什么
生成P1 配置骨架dev 彩色 / prod 单行 JSON，processor 顺序排对
P2 请求上下文request_id 自动发号，user_id 鉴权后绑定
P3 脱敏处理器输出前统一抹掉敏感值，不靠人记得
审查P4 凌晨三点演练让它站在查日志的人那边，指出缺哪个字段
P5 全项目扫一遍把存量 print 和 f-string 一次性列成清单
提示词 01 · 配置骨架（完整版）
现场：项目 fly-agent，FastAPI + structlog。日志目录从 settings.LOG_DIR 读，按天分文件。
      现有 app/core/logging.py 里是一份别人写的 260 行配置，我要重写成能讲清楚的最小版。

任务：写 setup_logging()，开发彩色、生产单行 JSON，一个开关切换。

契约（这几条一个字都不许改）：
1. event 名一律 lowercase_with_underscores，写「什么发生了」，不写句子、不带标点。
   错的：f"User {uid} logged in"    对的：logger.info("user_login_succeeded", user_id=uid)
2. 任何 logger 调用里不许出现 f-string 或字符串拼接
3. 开发环境用 ConsoleRenderer；其他环境用 JSONRenderer，且一条日志必须严格一行
4. 时间戳统一 ISO 8601 带时区，不做本地化
5. 上下文变量（request_id / user_id / session_id）由 processor 统一注入，
   不许在任何调用点手写
6. 这一步只写配置，不要写中间件、不要写脱敏

验收：
- 开发环境打一条日志，终端彩色、一眼能读
- 切成 production 重启，同一条日志是一行合法 JSON，jq . 不报错
- 任意业务代码 logger.info("x", user_id=1)，输出里必须自动带 request_id

输出：完整的 app/core/logging.py，外加一段说明：processors 列表为什么这么排、
哪两个位置互换会让 request_id 或脱敏静默失效。

最后那句是这条提示词的价值所在。日志配置最反直觉的地方就是顺序决定字段还在不在，而且排错不报错。让它解释一遍，你才知道自己贴的是什么。

提示词 02 · 请求上下文（契约骨架）
上下文：日志已用 structlog，processor 里已注入 request_id。

要它做到：user_id 和 session_id 自动出现在同一次请求的每条日志里。
必须写死的三条：
- 只在鉴权成功后 bind 一次，不在各调用点手写
- 每个请求开头 clear 一次，否则协程复用时字段会串
- 响应头回写 X-Request-ID，用户报障时直接要这个

输出：中间件与依赖注入两处改动 + 一句说明为什么用 contextvars 而不是全局变量
提示词 03 · 脱敏处理器（契约骨架）
要它做到：在日志输出前统一抹掉敏感值。
必须写死的四条：
- 命中 password / token / authorization / cookie / secret / api_key 时，值换成 ***
- 大小写不敏感
- 必须挂在渲染器之前
- 先拷贝再改，不动调用方传进来的原始 dict

验收句话：用错密码登录一次，全库搜不到明文；jq 取出来是 ***
输出：函数本体 + 它在 processors 列表里的确切位置
提示词 04 · 凌晨三点演练（审查）
你现在是凌晨三点被叫醒的运维。手上只有一个 request_id 和这台机器的日志文件。
用户说「它刚才卡了」。

对着这段日志回答三件事：
1. 这次请求经过了哪些模块，按时间排出来
2. 卡在哪一步、卡了多久
3. 哪条日志本可以省掉、哪条本可以更细

答不上来的地方，直接指出缺哪个字段。不要改代码，先只报缺什么。
提示词 05 · 全项目扫一遍（审查）
任务：扫一遍全项目的日志调用点，找出四类问题——
print 打的 / f-string 拼的 / logger.error 没带堆栈的 / 手写 user_id 的。

输出：一张表，四列 = 文件:行号 / 问题类型 / 当前写法 / 建议改法。
只报不改，等我按优先级挑。改的时候一次只改一个文件。
三条最容易踩的反模式

① 「帮我加个日志」。你会得到一堆 print 和 logger.info(f"...")。它能跑，只是三个月后一点用没有。

② 只说「要结构化」。它会给你 JSON，但 event 全是句子、字段名随心情变 —— 格式对了，契约没对。

③ 不让它解释 processor 顺序。你贴进来一段自己看不懂的配置，之后想加个字段，动一个位置就全废，而且不报错。

它给错了的时候，用这三句话追问

「把 processors 列表按顺序解释一遍，哪两个调换位置会让 request_id 消失？」

「这段日志如果三个月后来查，缺什么？只列缺的字段，别改代码。」

「只改 app/core/logging.py，其他文件一个字都不要动，把上次顺手改的退回去。」

一句话带走日志的提示词不是让它写，是让它审——因为错不会自己冒出来。

7收口：上生产之前，还有三件事

第一件：本机这份文件，只是本地的便利

生产上日志不该住在容器里

容器一重启，写在里面的 jsonl 就没了；跑三个副本，三份日志各写各的，查一次事故要开三个终端。 生产上的通行做法是进程只往标准输出写，由容器运行时或采集器（Fluent Bit、Loki、云厂商日志服务）收走统一存。 本课按天分文件的那套，是给你本地开发和单机演示用的。

判断依据很简单：这份日志会不会随进程一起消失？会，就不能指望它做故障复盘。

第二件：七条避坑

#坑正确做法
1用 f-string 拼日志事件名固定，变量放进 kwargs
2事件名写成句子或中文小写下划线，主体_动作_结果
3出错用 logger.error 不用 logger.exception现场没有堆栈，等于只留了一句话
4把整个请求体塞进日志单条超 8 KB 会被截断，还带一堆不该留的数据
5每个调用点手写 user_id迟早在最关键那条上漏掉，改用 bind_contextvars
6脱敏处理器排在渲染器后面静默失效：日志照打，明文照留
7生产只写本地文件走标准输出交采集器，别指望容器里的文件

第三件：考点速查

P0 必会为什么不能用 f-string 打日志；一条可用日志的五个必填字段；ERROR 为什么必须带堆栈。

P1 常问文本日志与结构化日志怎么取舍；request_id 怎么贯穿一次请求；日志级别怎么判断。

P2 加分contextvars 为什么能按协程隔离；processor 顺序为什么决定字段存亡；日志量太大时怎么采样。

日志这一块通了之后，前面写的认证、后面要接的 Agent，才有办法在出问题时被看见。 下一课接 LangGraph 的时候，每一次节点跳转、每一次工具调用，都可以用同一套 event 命名接着往下写 —— 你会第一次看到，一次完整的请求在日志里长成一条可以读的时间线。

一句话带走生产上日志不该住在容器里，它应该流出去。
