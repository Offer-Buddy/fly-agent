换个窗口就失忆，塞满历史又变笨

Agent 的记忆是个典型的「看起来简单、选错就翻车」的地方：全塞进上下文，账单和噪声一起涨； 接个向量库，又发现它记住了不该记的。这一篇把六种记忆方案摊平了比， 再用两张打分表，给「这一层该用哪个」定出能说清理由的结论。

1三种病，别当成一种治

上线第一周，你大概会先收到一条这样的反馈：

「我上周不是跟你说过我在做政务项目吗，怎么又问一遍。」
紧接着第二周是账单，第三周是更糟的东西——A 客户问「我的项目进展如何」，回答里冒出 B 客户的项目名。

这三件事听着都像「记忆没做好」，但它们的病根完全不同，修法也互相冲突： 给第一种加记忆，第二种会更贵；给第二种做压缩，第三种照样串。

病症现象真正的病根落在哪一层
失忆 同一个用户，换个会话，Agent 又从头认识他一遍 记忆的生命周期被绑死在会话上。会话结束，记忆跟着消失 缺长期记忆
撑爆 对话越长越慢越贵，第 30 轮说过的那句约束，第 40 轮它就不认了 把「过程」当「结果」存。上下文是工作台，不是档案柜；塞得越满，中段信息越容易被忽略 工作记忆没做减法
串号 A 的偏好出现在 B 的回答里 隔离键缺了或者没带上：写入没带 user_id、检索没做过滤、缓存 key 少了人 三层都可能是漏点
先算一笔账，看清「撑爆」有多快

50 轮对话、每轮 300 token，全塞进上下文就是 1.5 万 token（50 × 300）。 单次不算贵，但每一轮都要重付一遍——第 50 轮那一趟，光历史就占掉 1.5 万。 更麻烦的是质量：关键信息落在长上下文中段时，模型的召回明显下降（业界称作 lost in the middle）。 你多花的钱，买到的是更差的答案。

所以先别问「用不用向量库」。先问一句：这条反馈，是记忆没写下来，是写下来但没取回来，还是取回来取错了人？ 这三个问句对应下面三章，也是你排查记忆问题的固定顺序。

一句话带走记忆的三种病——记不住、记得太贵、记串了，修法互相冲突，得分开治。

2本质：四个动作，三层楼

不管叫记忆、上下文、知识库，落到代码里都只有四个动作。六种方案的差别，全在这四步上各做了不同的取舍。

四步各有各的坑

动作这一步要定的事六种方案的差异点
写入谁来决定「这条值得记」规则写死最稳但最僵；模型抽取最灵活，但会抽错；让人自己写最准，但没人愿意写
存储放哪、活多久、怎么隔离窗口里活一轮，检查点活一个会话，向量库活几个月，文件活到你删它
检索这次要取回哪几条全量取回不筛选；滑动窗口按时间；向量按语义；图谱按实体关系
注入取回来怎么塞给模型拼进系统提示最省事也最容易被忽略；当工具结果返回，模型才会「主动去查」

三层楼：每层只干一件事

层管什么生命周期忘了会怎样用多了会怎样
工作记忆这一轮回答问题需要的全部材料一次请求答非所问，抓不住当前这句token 暴涨，中段信息被忽略
会话记忆这次对话已经发生过什么一个会话每轮都要重复背景，追问失效状态越滚越大，写库变慢
长期记忆这个人是谁、要什么、不要什么天 / 月级每次都从零认识用户记进无关噪声，反而误导回答
核心认知：三层混一层做，一定出事故

最常见的错法只有一种——把长期记忆塞进会话记忆里干：把所有历史都挂在 thread 上，指望它顺便记住用户是谁。 结果会话越重，跨会话还是零；再想跨会话，就把 thread 数据整段拷给下个会话，于是串号、膨胀、过期一起来了。 三层的隔离键也不同：工作记忆按请求，会话记忆按 thread_id，长期记忆按 user_id。隔离键选错，等于三层全废。

一句话带走记忆选型不是一道选择题，是三层各选一次；隔离键选错，三层全废。

3六种方案，各归各位

下面六种是工程里真正在用的做法。看的时候盯住三件事：存的是什么颗粒度、靠什么取回来、代价落在谁身上。 最后一项最容易被忽略——代价往往不落在「钱」上，而落在「召回不准」和「维护成本」上。

01全量上下文
整段对话原封不动全塞进去。不建库、不抽取、不做任何判断。
好在哪零代码零依赖；信息完全无损，相关性交给模型自己判断；天然是多轮对话的基线。
代价token 随轮数线性涨；长上下文中段的信息会被忽略；窗口有硬上限，迟早撞墙。
什么时候用单轮问答、十几轮以内的短会话、以及做对照实验的「对照组」。它不是落选方案，是基线。
02窗口 + 摘要
最近 N 轮保留原文，更早的内容用一次模型调用压成一段摘要，滚动更新。
好在哪成本立刻可控；实现只要一次 LLM 调用；能把「聊过什么」带到很久以后。
代价摘要是有损压缩，数字、专有名词、硬约束最先被抹掉；摘要会漂移，越滚越像套话。
什么时候用长对话的「过程记忆」。它记的是剧情，不是用户画像——别拿它当长期记忆用。
03会话检查点
把图状态（消息、中间变量、停在哪个节点）按 thread 存成快照，下一轮直接接着跑。
好在哪断线重连不丢上下文；工具调用、人工确认中断后能原地续跑；框架原生支持，写几行就通。
代价只管一个 thread，跨会话一个字都不共享；状态随轮数增长，写库有额外 IO；要靠清理策略兜底。
什么时候用多轮 + 可能中断的 Agent 主链路。它是「会话记忆」的标准答案，不是长期记忆的替代品。
04向量长期记忆
让模型从对话里抽出「一条一句的事实」，做 embedding 存进向量库，每次按语义召回 top-k。
好在哪真正跨会话；按语义召回，问法变了也能找到；可增删改做冲突消解；写入能异步，不进响应链路。
代价抽取要过一次模型（延迟 + 成本 + 抽错的可能）；精确字段容易漏；多一套库要运维。
什么时候用多用户产品要「认识这个人」：偏好、背景、长期目标。这也是本项目的选择。
05图谱记忆
抽成「实体 + 关系 + 有效期」的图，事实过期不删除，而是把那条边标成失效。
好在哪能回答「现在还有效吗」；支持多跳关系（人 → 公司 → 项目）；冲突可追溯，不会越记越乱。
代价建模与抽取成本最高；生态和文档都少，出问题难排查；数据量小时纯属浪费。
什么时候用事实本身会随时间变化、且必须能追溯的场景：合同、医疗记录、客户档案。
06文件式记忆
一份人可读的 markdown（MEMORY.md 一类），分区写偏好、项目约定、待办，Agent 自己读写。
好在哪完全透明，你能直接打开改；零依赖、可进 Git、离线可用；出错时一眼看得到哪句写歪了。
代价没有检索，靠全文塞进提示；无法按用户隔离；条数一多，它就变成第二份「撑爆的上下文」。
什么时候用单人自用的 agent、团队共享的协作约定、以及任何「需要人审一遍才敢生效」的记忆。

这六种不是竞品，是分层。真实系统里通常同时存在三种：检查点管续接、向量库管认人、上下文管这一轮。 面试里问「你们记忆怎么做的」，答「用了 mem0」是不及格的，答「三层分别是什么、各自的隔离键是什么」才算过。

一句话带走六个方案没有「更好」，只有「这一层的这一步该谁干」。

4打分选型：两个决策点，各选一次

打分不是为了算出一个总分然后服从它，而是逼自己为每一分说出理由。分数只是把「感觉」摊到台面上， 让你发现自己的偏好其实是某一两个维度撑起来的。

评分制 8 个维度 × 1–5 分，满分 40 方向 各项都是「分越高越好」，上手难度已做反向处理

方案结论分数背后的一句话理由
向量记忆选它唯一同时满足「跨会话」「按语义召回」「按 user_id 隔离」三项的方案，且能落进已有的 PostgreSQL
文件式备选上手快、透明，但业务适配只有 2 分：它没有隔离键，也没有检索，多用户场景下两条都是硬伤
图谱不用5 分的演进弹性是真的，但建模与排查成本在「偏好与背景」这类模糊事实上换不回等价收益
不做不用29 分不算低——它省下的是真实成本。它输在适配 1 分：用户会被反复问同样的问题

落选者什么时候该用

只夸赢家的选型是宣传，不是选型。这四种方案换一个场景，结论会直接翻转：

方案反过来选它的场景
全量上下文单轮问答、短会话、或者你在给「记忆到底有没有用」做基线对照。这时候上向量库是给自己加戏
窗口 + 摘要超长对话、以「聊到哪了」为主的产品（写作、陪伴、客服工单），摘要比向量更贴题
图谱记忆里的事实会过期、且必须能回答「当时是什么」——合同、医疗、客户档案、工单历史
文件式只有你一个用户、数据就在本机。这时候它比向量库更好：你能直接打开改，错了当场就能修
选型结论

1. 会话内用检查点：按 thread_id 存快照，状态里同时留 messages 和本轮检索到的记忆文本。

2. 跨会话用向量记忆：一条一句的事实 + embedding 落 pgvector，写入异步，检索按 user_id 过滤。

3. 不做图谱、不做文件式：前者在这个数据量下换不回成本，后者没有隔离键。

4. 三层都保留一个「关掉它」的开关，方便做对照实验——没有开关的选型，永远不知道它到底贡献了什么。

最容易踩的坑

把分数当结论。32 比 30 高 2 分，不代表向量记忆在你的场景里一定更好，只代表在「你自己定的这 8 个维度」下略优。维度和权重变了，结论就该跟着变。

忽略隔离键这一列。上面两张表里没有「多用户隔离」这一维度，因为它是门槛不是加分项——不满足的方案直接出局，不参与打分。

一句话带走打分表的价值不在总分，在逼你为每一分说出理由。

5判断标尺：四个问句，几条硬线

换一个项目，你未必有耐心再打一次分。那就记住四个问句，按顺序问下来，结论基本就定了。

#问句答「是」意味着什么答「否」意味着什么
1这条信息要不要跨会话？进长期记忆。会话结束它也得活着只做窗口 + 摘要，到此收工
2记的是精确字段，还是模糊背景？向量检索会漏，考虑结构化表或图谱向量记忆正合适，语义召回就是干这个的
3谁来写？规则、模型，还是人？模型抽取最省人力，但必须配一条「不写什么」的清单人写最准，用文件式；规则写最稳，但只有确定的场景适用
4写错了能不能撤回？需要更新与失效机制，不是只追加可以只追加，先跑起来再补

几条硬线（数字都带来源）

项建议值为什么是这个数
单轮注入的记忆文本≤ 1500 token再长就开始挤占正文，模型对「记忆段」的注意力也会摊薄
单条事实长度≤ 120 字项目里的抽取提示词就这么约束的：一条一事实，长了就变成模糊总结
召回条数 top-k3–5 条再多，召回率涨一点、准确率掉一截；噪声比缺失更伤答案
检索缓存 TTL60s项目默认值。同一窗口内重复提问不重复查库，超过这个窗口就该重查
写入方式后台异步抽取要过模型，几百毫秒起。串在响应链路里，用户会以为是「卡了」
记忆检索 P90 增量≤ +300ms超过这个数，用户开始能感知到「这次回复慢了一拍」
embedding 维度定死，别混项目用 1536。换模型必须整表重建，新旧向量不能放在同一列里比距离
隔离键user_id 必填匿名会话直接跳过记忆，不要把所有匿名用户塞进同一个分区

写入三纪律

记忆系统里，写什么比怎么取重要得多。取多了一条，答案啰嗦；写错一条，答案就带着错误的前提往下走，而且会一直错下去。 三条纪律：

纪律做法写错的后果
只写用户说的喂给抽取器的只有用户消息，助手回复一个字都不进助手提的建议被记成「用户偏好」，于是它开始按自己的建议服务自己
一条一事实不写「用户在做一个政务项目且喜欢简洁回答」，拆成两条合成一条后无法单独更新；改一半就得整条重写
带时间、可失效能判断时效的事实，要么写时间点，要么标明「截至」半年前的目标被当成现在的目标，回答一直走偏

「写 / 不写 / 更新」判定表

判定典型输入处理
写「我在杭州做政务系统，以后回答尽量简洁」抽成两条：所在地与行业、回答风格偏好
不写「你觉得 FastAPI 和 Flask 哪个好？」这是提问，不是陈述。抽成「用户关注 FastAPI」就是噪声
不写「好的，就按你说的办」用户只是认同了助手的建议，不是自己宣布了一个稳定偏好
更新「我换城市了，现在在深圳」把旧的那条标失效，写新的那条；不是再追加一条「用户在深圳」
删「别再记着我之前那个项目了」按条删除，并让缓存立刻失效，否则 60s 内还会取回旧值
记忆抽取提示词 · 骨架（照这个结构写，别写成一篇文章）
你只从「用户消息」里抽取关于用户的长期事实。
长期 = 这条事实会改变助手在将来某次无关对话里的回答。

# 抽取
- 身份：称呼、职业、所在地、语言
- 对回答方式的偏好：语气、格式、长度
- 稳定约束：过敏、饮食禁忌、必须回避的工具
- 明确承诺的长期目标（要具体到能行动）
- 有具体节奏的习惯（星期几、几点、时区）

# 不抽取
- 问题本身（「X 好不好？」不是事实）
- 助手说过或提议过的任何内容
- 本次会话任务的复述
- 寒暄、致谢、只有一个表情的回复
- 从名字或上下文推测出来的属性（性别、年龄）

# 格式
- 第三人称，以「用户」开头
- 单句自洽，不出现指代句外的代词
- 一条一事实，每条 ≤ 120 字

只返回 {"facts": [...]}，没有就返回 {"facts": []}。
这份提示词为什么值得抄

它的价值不在「抽了什么」，而在「不抽什么」那一段。绝大多数记忆系统的噪声，都来自把提问、把助手的话、把本次任务复述成了用户属性。 写这段清单，比调 embedding 模型划算得多。

一句话带走记忆写错比不写贵十倍——先管住写什么，再谈怎么取。

长期记忆：读先查缓存，写只写用户那一句 五个判断，缺一个就会出问题
python · 检索：缓存 → 向量库 → 回填
class MemoryService:
    async def search(self, user_id: str | None, query: str) -> str:
        if user_id is None:                      # ① 匿名会话不进长期记忆
            return ""

        key = cache_key("memory", str(user_id), query)   # ② key 里必须有人
        cached = await cache_service.get(key)
        if cached is not None:
            return cached

        memory = await self._get_memory()
        results = await memory.search(user_id=str(user_id), query=query)
        text = "\n".join(f"* {r['memory']}" for r in results["results"])

        if text:                                 # ③ 只缓存成功且非空
            await cache_service.set(key, text)
        return text
python · 写入：只取最后一条用户消息，且不阻塞响应
    async def add(self, user_id: str | None, messages: list[BaseMessage]) -> None:
        if user_id is None:
            return

        user_text = latest_user_text(messages).strip()   # ④ 助手回复刻意排除
        if not user_text:
            return

        memory = await self._get_memory()
        await memory.add(
            [{"role": "user", "content": user_text}],
            user_id=str(user_id),
        )

四个注释就是四条经验：匿名不写、缓存 key 带人、只缓存成功、只喂用户消息。 第四条尤其要紧——把助手回复一起喂进去，抽取器会把助手提的建议当成你说的偏好，于是它开始按自己的建议服务自己。

这两次查询互不依赖，串着写就是白白多等一次往返（项目里这一处省下的是 200–500ms）。 记忆文本作为图状态的一个字段进去，最后拼进系统提示——它是「注入」，不是「工具」：模型不需要主动去查，它每次都能看见。

注入 vs 工具，怎么选

注入：每次都在，简单，但占 token，且模型无法拒绝无关记忆。
工具（让模型自己调 search_memory）：省 token，可多次查，但模型可能压根不调。
经验做法：高频必备的少量事实走注入，低频可能要用的大量档案走工具。

档位你要做到

跑通会话 A 说「我在杭州做政务项目」，另开一个会话问「我在哪个城市」，答对；换一个用户问同一句，答「不知道」

七个坑，都在这条链路上

#坑正确做法
1把整轮对话喂给抽取器只取最后一条用户消息；助手回复一律排除
2匿名会话共用一个记忆分区user_id 为 None 直接跳过，宁可不记
3向量模型和对话模型共用一个端点嵌入走独立配置——不少供应商根本没有 embeddings 接口
4记忆写入串在响应链路里后台任务；失败了只记日志，不影响本轮回答
5把空结果、错误结果也缓存了只缓存成功且非空；否则一次抖动会污染整个 TTL 窗口
6换 embedding 模型不重建索引维度与语义空间都变了，旧向量必须整表重算
7服务启动后第一句就慢启动时预热：建连接池、跑一次 schema 检查（项目里这一步省掉约 130ms）
一句话带走检查点管续接，向量库管认人；写入永远异步，隔离键永远必填。

8决策树：按图定方案

不想打分的时候，按这张图走。它的第一问不是「语料多少条」这种阈值，而是判断维度—— 因为阈值会变，维度不会。

每一路的「不听更贵方案」理由

单用户自用：向量库能做的，一份 md 也能做；而 md 多出来的那件事——你能直接打开改——向量库做不到。

多用户偏好：图谱能表达的关系，在你这里其实没有；为了「可能有一天要问当时」付建模成本，是提前负债。

事务型事实：向量库答不了「这条还有效吗」，而这类场景里，答错一个失效事实的代价高于所有构建成本。

图外备注（阈值只当经验值，不当判断依据）

记忆条目在几千条以内，向量检索的召回质量足够；上万条之后才开始感到「相似但不相关」的噪声压力，这时候再考虑加结构化字段或换图谱。 这条是备注，不是分支条件——它的数值会随 embedding 模型和语料变化，拿它当第一问会把特例讲成通则。

底线只有一句：先用最便宜的那层打底，等真实投诉指明升级方向。「用户抱怨记不住」指向加记忆，「用户抱怨记错了」指向收紧写入，两者不是同一副药。

三道面试题，答完就知道自己懂没懂

问题及格线答法
「你们 Agent 的记忆怎么做的？」先分三层说：检查点管会话续接、向量库管跨会话事实、上下文管本轮。再补一句隔离键各不相同
「为什么不用全塞上下文？」成本随轮数线性涨，且长上下文中段信息会被忽略——多花的钱买到更差的答案
「记忆记错了怎么办？」先收紧写入（只写用户陈述、一条一事实、带时间），再谈检索；写错比不写贵十倍

考点速查

P0 必会三层记忆的分工与各自的隔离键；检查点的 thread_id 从哪来；长期记忆为什么必须带 user_id 过滤。

P1 常问为什么写入要异步、助手回复为什么不进抽取器；摘要与向量记忆各自解决什么问题；top-k 为什么是 3–5。

P2 加分图谱的时间边怎么处理事实失效；注入与工具化记忆的取舍；embedding 换模型为什么要整表重建。

走完这一篇，你应该已经能对任何一个 Agent 项目回答同一个问题： 它的记忆在哪一层、靠什么取回、隔离键是什么、坏了怎么发现。 这四个问题答得出来，选型就不再是「大家都在用 mem0 所以我也用」。
