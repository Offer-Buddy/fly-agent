1单 Agent 什么时候不够用P0

三个信号，出现任意一个，就该考虑拆分。注意是「信号」，不是「感觉」。

信号一

工具超过二十个

候选工具一多，模型选错的概率陡增。它不会告诉你「我不确定」，它会自信地选一个错的，然后编个理由。

信号二

三类知识挤在一个上下文

查制度、算金额、写文书，三种任务需要完全不同的背景材料。塞在一起，模型会被无关信息带偏。

信号三

不同环节要求不一样

检索要便宜快、写文书要强模型、涉及金额要严格权限。一个 Agent 配一套参数，满足不了三种要求。

最常见的错误理由：「多智能体显得更专业」。它带来的成本是数倍 token、数倍延迟、数倍调试难度。拆分的前提是撞到了上面三个信号之一，而不是想让架构图好看。

还有一个更隐蔽的成本容易被低估：拆分会让「改一处」变成「改三处」。单 Agent 改个提示词就完事的地方，拆分后要同步改路由描述、子 Agent 提示词、以及回收判断逻辑。这笔账在需求稳定前是亏的。

拆分的前提是撞到三个信号之一；为了架构图好看而拆，是最贵的自嗨。

2四种多智能体拓扑P0

多智能体不是只有一种形状。按「谁掌握控制权」分，主流是四种：

Supervisor中心调度

可审计。每一步为什么这么走，都在调度者的决策里。代价是它成了单点。

Handoff / Swarm控制权移交

天然贴合转接。客服分诊最顺手；多跳之后没人知道全局状态。

Hierarchical分层调度

能扩到很多子域。代价是一次请求的调用树很难看清。

Network任意互联

只适合探索。路径不可预测、不可复现，生产基本不用。

四张图放在一起看，差别只有一句话：控制权在哪儿。第一张在中心，第二张跟着对话走，第三张分了两级，第四张散在每个人手里。

拓扑控制方式适合主要风险
Supervisor
中心调度		 一个调度者持有全部控制权，子 Agent 之间不直接对话 环节清晰、需要审计、需要知道「每步为什么这么走」的业务流 调度者是单点；它判断错，整条链都错
Handoff / Swarm
控制权移交		 当前 Agent 直接把对话交给下一个，自己不保留调度权 客服分诊、对话式路由，场景天然是「转接」 交出去容易收不回来，多跳之后没人知道全局状态
Hierarchical
分层调度		 Supervisor 管 Supervisor，逐层下放 子域极多、单层管不过来的大型系统 层级一多，一次请求的调用树很难看清
Network
任意互联		 Agent 之间自由通信，没有中心 研究探索、开放式协作实验 不可预测、不可复现，生产基本不用
Supervisor 的本质，是把不确定的协作收敛成一条可审计的主线。代价是所有判断压力都压在调度者身上——所以它的路由质量，直接决定整个系统的上限。

选 Supervisor 的理由通常不复杂：业务环节明确、需要知道每一步为什么这么走、出问题要能指到具体是哪次委派。这三条正好是 Supervisor 强、Handoff 弱的地方。

一句话区分 Supervisor 和 Handoff：Handoff 是「你接着聊，我下班了」；Supervisor 是「你去办，办完回来给我」。前者转移责任，后者只转移任务。
Supervisor 只转移任务、不转移责任；Handoff 把责任一起交出去了，所以难收口。

3Supervisor 的运行闭环P0

一次用户请求，在 Supervisor 里走四步，可能循环几轮：

这四步里最容易被做坏的是第 ② 步。委派时把前面三十轮对话整个塞给子 Agent，它抓不住重点；只给一句话，它又缺关键约束——比如「金额单位是万元」这种前提没说，算出来差四个零。

所以委派要有一个固定结构，不是随手拼一段话：

简报要素写什么不写的后果
任务目标一句话说清要产出什么，不是要干什么活子 Agent 做了一堆事，没有一件是你想要的
必要上下文只给完成这个任务必需的信息，其余不放信息过载，子 Agent 抓错重点
约束条件单位、口径、时效、不能用哪些数据结果形式对、数值全错
产出格式要结构化还是自然语言、要几个要点回收时无法被下游直接使用，还要再加工一遍
不许做什么明确禁止的动作，比允许清单更有效子 Agent 「顺手」做了一件不该做的事
记住一句话：Supervisor 不干活。它不检索、不算数、不写正文。它只做两件事——决定谁上，决定什么时候停。判断力是它唯一的资产，一旦它开始自己动手，拆分就失去意义了。

这也解释了一个常见现象：Supervisor 的提示词应该很短，短到只有「你是谁、有哪几个下属、各自负责什么、什么时候必须停」。如果它的提示词比子 Agent 还长，说明它在越权干活。

Supervisor 不干活，只决定谁上和什么时候停；它的提示词越短，说明职责越干净。

4四个死穴P0

死穴一：路由漂移

症状：子 Agent 交了结果，Supervisor 觉得「还不够」，又派给另一个；第二个也交回来，它还是不满意，再派回第一个。用户等了几十秒，什么都没拿到。

处方：给调度设硬性轮次上限（比如最多三轮委派），到上限就强制收口——哪怕答案不完美，也要给出「目前掌握的情况 + 还缺什么」。有缺陷的回答，好过无限等待。

死穴二：上下文失真

症状：两个极端。要么把全部历史丢过去，子 Agent 被无关信息淹没；要么只给一句话，子 Agent 缺关键前提，答得离谱。

处方：用上一节那张简报结构。核心原则是「委派要像给同事派活，不像把聊天记录转发给他」——你不会把一个三十页的群聊记录甩给同事说「你懂的」。

死穴三：无限委派

症状：A 交给 B，B 觉得该找 A，A 又交给 B。或者子 Agent 在自己的循环里绕圈，每次都在「再查一次」。

处方：两层预算——全局步数预算（一次请求最多产生多少次模型调用）+ 重复检测（相同工具 + 相同参数出现两次就中断）。预算要写进配置，不能靠提示词「请不要重复」。

死穴四：调试黑洞

症状：一次用户请求产生二十次子调用。用户说答错了，你打开日志，看到一坨交错的时间线，完全不知道哪一步开始跑偏。

处方：每次委派必须带同一个请求标识，并且有独立的追踪段。理想状态下，你能一眼看出「第 3 次委派给检索 Agent 时，它拿到的上下文里缺了时间范围，所以检出了去年的数据」。

这一条最容易被忽略：多智能体的调试成本不是线性增长的。三个子 Agent 的组合路径已经超过十种，靠读日志基本不可能定位问题——可观测性必须在第一版就做，不能等出事再补。
四个死穴的共同解药是硬预算、结构化简报、可追踪的委派——三者缺一，多智能体就变成黑洞。

5六个必须提前定的设计决策P0

这六个问题如果不在开工前定，会在开发第二周以「返工」的形式回来找你。

决策常见选项怎么选
子 Agent 粒度 按能力切（检索 / 计算 / 写作）
按业务环节切（受理 / 审核 / 出件）		 按能力切复用高、边界稳定；按环节切好审计、贴近业务。业务方要看懂就按环节，工程复用优先就按能力
状态共享 全体共享一份消息历史
各自独立状态 + 显式传递		 共享简单但互相污染，独立干净但要设计交接格式。子 Agent 超过三个，建议独立状态
路由方式 模型路由 / 规则路由 / 混合 流程稳定的部分用规则（快、免费、可预测），开放意图用模型。生产上基本都是混合，不要纯靠模型
终止条件 轮次上限 / 判据满足 / 人工确认 三个都要有。轮次上限兜底，判据满足是正常出口，人工确认留给高风险场景
失败处理 重试 / 降级到通用 Agent / 直接上报 可重试的错误重试，能力缺失降级到通用 Agent，权限或数据问题直接上报——别让 Agent 自己想办法绕过限制
人工介入点 高危动作前 / 终稿输出前 不可逆动作（付款、删除、对外发送）必须前置审批；内容类任务在终稿前设一次确认即可
六个决策里最重要的是前两个。粒度和状态共享一旦定错，后面四个都会跟着拧巴——因为路由方式、终止条件、失败处理都建立在「谁持有状态」这个前提上。
六个决策里，粒度与状态共享是地基；这两条定错，其余四条怎么调都不顺。

6画出你的拓扑P1

动手练习

一张纸画完，必须标出四样东西

  • 一个 Supervisor + 三到五个子 Agent，每个子 Agent 旁边写它的职责（一句话，动词开头）
  • 每个子 Agent 有什么工具，特别是：谁有写权限
  • 什么情况下必须停——轮次上限几次、哪个动作前要人确认
  • 谁失败了谁兜——画一条备用路径出来

画完互相问一个问题：「把 Supervisor 拿掉，这个流程还能不能跑？」如果能跑，说明你其实不需要 Supervisor，只是需要一条固定的流水线。这个问题能筛掉一半过度设计。

自检四条：子 Agent 之间有没有直接对话（有就说明控制权漏出去了）／ 委派简报里有没有「不许做什么」／ 全局预算写在哪／ 一次请求最多产生多少条追踪记录。
拿掉 Supervisor 流程还能跑，就说明你不需要它——这条自检能筛掉一半过度设计。
