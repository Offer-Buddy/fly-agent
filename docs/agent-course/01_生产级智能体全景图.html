1什么是 Agent：一个模型，加一套 HarnessP0

先破一个误解：Agent 不是「提示词写得更聪明的聊天框」。两者的分界线只有一条——它能不能自己决定下一步。

聊天框：Prompt + LLMAgent：LLM + Harness
一轮怎么走你问一句，它答一句，结束你给一个目标，它自己决定查什么、调什么、什么时候停
中途出错只能由人重新提问、重新组织语言它自己看结果、改参数、换一条路再试
能力上限模型训练时见过的那些模型 + 你给它的工具、数据、记忆

所以业内给了一个极简的公式，几乎所有 Agent 框架都可以拿它来解释：

Agent = LLM + Harness一个是大脑，一个是挽具：前者租得到，后者得自己搭

LLM 是一个纯函数。丢一段文本进去，吐一段文本出来，中间不留痕、外面不伸手。它能想，但有四件事它做不到——而 Harness 存在的全部理由，就是补这四件事。

它不记得

每次调用都是全新的：窗口一关，上一轮就归零。

它没有手

只能输出文字，查不了库、下不了单、改不了表。

它不会绕圈

一次生成就结束，不会「看完结果再决定下一步」。

它不知道边界

不会自己停，不识别越权，也不知道这一轮花了多少钱。

补上这四件事的那一整套，就叫 Harness。这个词原本指马具里的挽具：马有力气，但要靠挽具才能拉车、才能被驾住。模型是马，能力上限由它决定；能不能把事办成，由挽具决定。

七个模块，各自替模型干一件事

按图上的位置走一圈，从正上方的编排开始，顺时针看：

模块对应哪一层它替模型干的那件事缺了会怎样
流控编排编排层决定下一步交给谁、什么时候停、走错了退回哪一步只能一问一答，永远没有第二轮
上下文工程记忆 + 知识调模型之前，把该给的信息挑出来、压到放得下的长度要么窗口溢出，要么塞一堆进去，模型抓不住重点
Model 大脑模型层读懂、推理、做判断，再把结论说出来——只负责想没有可想的，只剩一个输入框
能力与执行工具层把「决定」变成对外部世界的真动作：查库、下单、发消息只能说，不能做
状态与检查点状态层记着跑到哪、每步产出了什么、崩了从哪接重启即失忆，长任务永远跑不完
安全与治理交付与安全划出能碰什么、碰坏了能不能查、谁能用、花多少封顶一次越权就是一次事故
观测与评估可观测与评测量出这一轮为什么这么答、改完是变好还是变坏坏了不知道，好了也不知道
大模型网关模型层 · 接入侧所有调用唯一的出口：路由、限流、缓存、计量、降级换一家厂商要改全站，账单失控也没人知道

对照讲义：「状态与记忆」在那边是一个模块。这里把记忆挪进了「上下文工程」——记忆和知识在输入侧本来就是同一件事；状态层则只留流程位置与快照。

为什么是「一个 + 七个」，不是「八个并列」？因为外圈这七块，每一块都可以单独换掉、单独不做；只有中间那块不能省——省了就没有智能。但真实情况常常相反：最容易替换的恰恰是中间那块。模型一年换一次，Harness 会跟你三年。所以投入顺序也是反的——先把挽具搭起来，再挑马。

还有一点容易被忽略：这七个模块不是七个抽屉，摆在那儿等你去取用。它们是同一轮请求里轮流被叫到的角色——有的每轮都进循环，有的只在旁边记录。按时间摊开，主链路和旁路就分开了：

Agent = LLM + Harness：模型负责想，其余七件事全靠外面这套挽具。

2八层：把责任边界划清楚P0

七个模块加一个大脑，落到评审文档里，习惯写成「八层」。层不是模块划分，是责任边界——判断一个东西该不该单独成层，只问一句：它挂了的时候，会不会拖垮别的层？

八层再分两组，两组的失败长相完全不同：下四层决定系统跑不跑得住，坏了的表现是崩、是慢、是闯祸；上四层决定它像不像懂业务、能不能交出去，坏了的表现是答得不对、说不清为什么。所以排查顺序也是这个顺序：先确认没崩，再问好不好。

#层组它负责回答的问题不做的后果
1模型层地基用哪个模型、按什么规则路由、挂了切到哪、一次调用最多等多久一家挂了全线挂
2编排层地基流程长什么样、在哪里分叉、什么条件下回退、谁来决定下一步业务逻辑烂在 if-else 里
3状态层地基跑到哪一步了、这一步的中间结果是什么、崩了从哪接重启即失忆
4工具层地基模型能调用什么、参数怎么校验、能并发几个、有什么权限瞎调、越权、互相踩
5记忆层能力这个用户是谁、上次聊到哪、长期偏好是什么每次都从零认识用户
6知识层能力答案的依据在哪、怎么切、怎么找、怎么证明不是编的答得流畅，全是编的
7可观测与评测能力这一轮为什么这么答、改完是变好还是变坏、花了多少钱坏了不知道，好了也不知道
8交付与安全能力怎么对外提供服务、谁能用、怎么限流、密钥放哪、成本上限多少演示永远只是演示
一个实用的自检：拿这八行当检查表，逐行问「如果这一层明天坏掉，我的系统会怎样」。答不上来的那一行，就是项目现在最大的风险敞口。
八层是责任边界，不是功能清单：下四层保命，上四层保真。

3下四层：模型 / 编排 / 状态 / 工具P0

模型层 · 决定系统的下限

四个动作：选型（谁主谁备）、路由（什么任务用什么模型）、降级（主模型挂了切谁）、预算（单次请求最多等多久、最多花多少）。

最常见的错法：只配一个模型，重试也没有总预算。结果是一次请求在失败重试里拖了 90 秒，用户早就走了，后台还在烧钱。

正确做法是设一条降级链：强模型 → 中模型 → 轻模型。每一档都设超时，整条链有一个总预算，超了就返回「稍后再试」，而不是无限重试。

编排层 · 决定系统的上限

编排层要回答的是「流程可见吗」。一个流程如果只能通过读代码才能说清，那它就没法被审计、没法被优化、也没法交给别人维护。

错法是把业务规则塞进提示词：「如果金额超过十万并且是首次合作，就……」。这种规则写在提示词里既不可测也不可查。正确做法是让编排层承担分支，提示词只负责理解与表达。

状态层 · 决定系统能不能活下来

三个概念必须分清：消息历史（聊过什么）、图状态（流程走到哪、各节点的中间产出）、检查点（某一时刻状态的快照）。

你以为实际
存了消息历史就叫有状态只有聊天记录、没有流程位置。断点续跑时不知道下一步该调哪个工具
用缓存存会话就够缓存是用来加速的，不是用来兜底的。缓存清了，审计链也断了
状态存在进程里最快最快，也是最快消失的。一次发布全部清零

工具层 · 决定系统会不会闯祸

工具层最容易出事，因为它直接对外部世界产生副作用。四件事必须做：

  • 参数校验——模型给的参数不可信，必须有 schema 约束，不合法直接拒绝而不是猜
  • 描述质量——工具描述是写给模型看的，不是写给人看的。说清「什么时候该用」比说清「内部怎么实现」重要得多
  • 权限边界——读、写、删必须分级；高危动作要么白名单，要么强制人工确认
  • 并发控制——几个工具同时跑时，谁先谁后、失败了怎么回滚，要提前定

换个画法就清楚了：工具调用不是「模型说调就调」，而是一条要过四道闸的链。

反面教材：把「删除」「退款」「发消息」这类不可逆动作直接开放给模型自主调用，是生产事故的标准配方。不可逆的动作，一律加一道人工闸门。
模型层决定下限，编排层决定上限，状态层决定能不能活，工具层决定会不会闯祸。

4上四层：记忆 / 知识 / 可观测 / 交付P0

记忆层 · 决定用户觉得你懂不懂他

记忆通常分四档：滑动窗口（最近 N 条）、增量摘要（把早期对话压成一段）、长期语义记忆（把事实抽出来存向量库，按需检索）、用户画像（稳定偏好，结构化存）。

最常见的错法是把「记住」当成「理解」：什么都往里存，结果检索出来的全是噪音，反而干扰判断。记忆的关键不是存多少，是该忘的能不能忘掉。

知识层 · 决定答案能不能被信任

一条完整的链路是：文档解析 → 切分 → 向量化 → 检索（向量 + 关键词混合）→ 重排 → 组装进上下文 → 生成时带引用。

只做向量检索是最常见的偷懒。专有名词、条款编号、型号这类精确匹配需求，纯向量检索经常查不准，必须配关键词检索做混合。

知识层的验收标准不是「答得像」，而是「答错了能被发现」。每一句结论都能回溯到原文的哪一段，这才是知识库和模型记忆的区别。

可观测与评测 · 决定能不能持续变好

两件事要分开看：可观测是「事后能还原」，评测是「改动可量化」。

  • 可观测要能回答：这一轮用了哪个模型、调了哪几个工具、每步耗时多少、花了多少 token、哪一步开始跑偏
  • 评测要有一套固定的题（黄金集），每次改动跑一遍，看总分和分类得分有没有退步

这两件事合起来，才构成一个能自我修正的闭环：

没有评测基线就调提示词，本质是玄学。你会陷入「感觉好了 → 上线 → 另一类问题冒出来 → 再改」的循环，而且永远说不清哪一版更好。

交付与安全 · 决定它能不能真的被用

这一层最不性感，但最容易被跳过：异步服务、流式输出、身份认证、限流、密钥管理、成本上限、容器化、日志脱敏。

判断标准很朴素：这套东西能不能交给一个不懂代码的同事，让他自己启动、自己重启、自己看日志。不能，就还停在演示阶段。

记忆的关键是会忘，知识的关键是能回溯，可观测的关键是有基线，交付的关键是别人能接手。

5层的耦合关系P1

八层不是八个独立的选择题，有几组是绑定的。选错一个，另一个也白选。

绑定组合为什么必须一起考虑
编排 + 状态选了图但没有检查点，等于用最贵的方式写了一个不能恢复的循环
记忆 + 知识两套检索混在一个上下文里会互相污染。用户偏好和业务事实必须分区，不能一锅检索
工具 + 权限工具越丰富，越需要权限边界。十个只读工具很安全，一个写工具就够出事
可观测 + 评测没有追踪就没有评测数据源。评测集里的题，答案往往要从真实轨迹里捞
模型 + 成本多智能体一开，token 消耗是单 Agent 的数倍。模型选型必须和预算一起定，不能分开
一个反直觉的推论：因为存在这些绑定，八层的实际自由度远小于八。你真正能独立决定的，大概是四到五个——其余都是被绑定的那一层替你决定了。
八层里有五组是绑定的，所以真正的自由度只有四到五个，别当成八道独立选择题。

6填一张八层地图P1

动手练习

为你的项目填一张八行表，每行三格

  • 候选——这一层打算用什么（可以写「自研」「先不做」）
  • 理由——一句话，必须能说出「为什么不是另一个」
  • 它挂了我怎么办——降级、重试，还是接受不可用

填完做一件事：把所有写「先不做」的行圈出来，判断它是故意不做还是没想到。前者要作为已知债务记下来，后者就是现在的风险敞口。

两种常见情况的处理：

  • 「知识层先不做，因为第一版只做工具调用不做问答」——合理取舍，但要在需求文档里写清边界，防止后期被当成缺陷。
  • 「记忆层先不做」但需求里明明写了「记住我的偏好」——这是自相矛盾，必须当场解决，不能留到开发中期。
八行都填完，你会得到一张自己的技术栈地图。下一页要把这张图的每一格，逐一变成带理由的决策记录。
写「先不做」的行要么是取舍，要么是风险敞口——分不清这两者，就等于把坑留给了三个月后的自己。

7小结：这一讲收成四句话P1

开头那个问题——同样接一个大模型，为什么有的只是聊天框，有的能把事办完——走到这里可以收口了。四句话，每句后面附一句「拿它干什么」。

01
Agent = LLM + Harness

模型能想，但不记事、没有手、不会绕圈、不知道边界。这四件事一件都不在模型里，全在外圈那七个模块——Harness 存在的全部理由，就是补这四件事。

看一个 Agent 产品强在哪，先数它外圈装了几层，再看它用了哪个模型。

02
不是八层并列，是 1 + 7

模型是大脑，编排、上下文、状态、工具、安全、观测围着它转；底部那层网关是所有调用的唯一出口，也是成本唯一发生的地方。

画架构图时，如果把模型画成和其他七个一样大的方框，这张图基本就画错了。

03
八层只有四到五个自由度

五组绑定：编排＋状态、记忆＋知识、工具＋权限、可观测＋评测、模型＋成本。其中一组定错，另一组必须跟着改。

排期别排成八道独立选择题，绑定的一起定，否则一定会返工。

04
「先不做」要分两种

故意不做是取舍，要写成已知债务并划清边界；没想到就是风险敞口，会在几个月后变成线上事故。两者在外表上完全一样。

八行表填完，把所有写「先不做」的行圈出来，逐个问：这是我决定的，还是我漏掉的？

还有一句要交代清楚：这一讲的视角是「一个 Agent 内部」。下一讲把镜头往外拉一层——同样是这些零件，按什么套路连起来、谁来决定下一步，得到的系统完全不同。五种范式、四种骨架、七个框架，讲的就是这件事。
能力上限由模型决定，能不能把事办成由 Harness 决定；八层里真正能独立拍板的只有四到五个。
