1三个词：范式、架构、框架P0

这三个词在讨论里天天被混用，后果很具体：把「我们该用 ReAct」和「我们该用 LangGraph」当成同一类问题来投票，最后选出来的是一个人气最高的库，而不是一套说得清的打法。

词它回答什么变化周期例子
范式这一类问题，该用什么套路去想、去解决很少变，几年才换一次主流工具循环 ReAct
计划-执行 Plan-and-Execute
反思 Reflection
多智能体 Multi-Agent
工作流编排 Agentic Workflow
架构系统里有哪些角色、状态归谁、失败怎么兜一个项目定一次，重构才动单环 Single Agent Loop
链加环 Chain + Loop
路由扇出 Router + Fan-out
编排者-工作者 Orchestrator-Workers
框架这套东西能让你少写多少行代码半年到一年换一茬LangGraph、CrewAI、Agents SDK、Dify

三者的关系不是并列，是一对多：一种范式可以用好几种架构实现，一张架构图可以用不同框架搭出来，一个框架通常内置了好几种范式——像一种做法能换好几口锅，一口锅也能做很多道菜。所以「选范式」和「选框架」是两个不同的决策，只是它们经常被一起讨论。

一个类比：做一道菜

范式 = 做法

清蒸、红烧、爆炒。同一块肉换个做法，风味和耗时全变；做法本身不分高低。

架构 = 分工

谁切配、谁掌勺、几口锅同时开、哪道菜先上桌。它是这一餐的安排，画得出来，也改得动。

框架 = 厨具

现成的炒锅、蒸箱、料理机。趁手能省一半力气，但不替你决定吃什么。

这个比喻能一直用下去，因为它顺手解释掉四件事：

  • 一对多　一种做法可以换好几口锅；一口锅也能做很多道菜。
  • 不分高低　清蒸不比红烧低级。三步的流程硬上自主循环，像用高压锅煮泡面——能煮，但没必要。
  • 换锅不等于换做法　把 Dify 换成 LangGraph，做法没变，端出来的还是那道菜。
  • 厨具不是入场券　没有蒸箱，锅上加个架子也能蒸；复杂到一定程度，成套厨具才值那个价。

三个最常见的混淆

  • 「我们用的是 ReAct 架构」——ReAct 是做法。你真正的架构是「单个 Agent + 工具白名单 + 步数上限 + 检查点」，只是恰好用了这个做法。
  • 「LangGraph 是一种范式」——它是厨具。链式、ReAct、多智能体它都能装，但不替你决定做哪道菜。
  • 「Supervisor 是范式」——它是架构层的形状（编排者-工作者）。每个被调度的子 Agent 内部，仍然要各自选做法。
一句话记住：范式决定「怎么想」，架构决定「谁在哪、状态在哪」，框架决定「少写多少行」。三者对齐，项目才顺；只对齐最后一个，前两个会在三个月后回来找你。
范式是做法，架构是分工，框架是厨具；先定做什么菜，再挑锅。

2五种范式：场景、做法与失效点P0

业界对范式的说法这两年收敛到五种：ReAct、Plan-and-Execute、Reflection、Multi-Agent、Agentic Workflow。前四种讲「智能体怎么思考和行动」，第五种讲「把这些思考方式编排成一条可交付的流水线」。

Anthropic 在《Building Effective Agents》里列的链式、路由、并行、编排者-工作者、评估者-优化者，基本都能落进最后两格里——链式、路由、并行属于 Agentic Workflow 的形状，编排者-工作者属于 Multi-Agent，评估者-优化者就是 Reflection。所以不用记两套，记住五种就够。

单次生成不算范式，它是所有范式的基线：不循环、不分工、不编排。先证明「一次能做对」，再谈要不要加步骤、加角色、加流程。

下面逐个拆，四段固定：解决什么、典型场景、最佳实践、失效信号。图里的每个方框代表一次模型调用或一次工具执行，箭头是数据流。形状比名字重要——开会时有人说「这里做个 ReAct 就行」，你得立刻反应过来他说的是哪种回路、会带来哪些代价。

01

工具循环 ReAct

想一步、做一步，看到结果再想

解决什么　让模型在「想 → 做 → 看结果 → 再想」的回路里自己决定下一步，路径不预先指定。它是所有自主 Agent 的原型。

典型场景　查库、查工单、先检索再作答、多轮排障，以及任何「看到结果才知道下一步」的任务。

失效信号　同一个工具被反复调用、参数越改越像——已经在绕圈了，该收口或换策略。

最佳实践

  • 把推理（Thought）显式写出来再决定动作，否则模型会跳过思考直接乱调工具
  • 工具控制在 10 到 15 个以内，描述写成接口文档：什么时候该用、什么时候别用
  • 三条硬上限——步数、时长、花费；到限优雅收尾并给出已完成的部分
  • 每次调用留痕（入参、返回、耗时），否则出错时无法复盘是哪一轮跑偏
  • 不可逆动作（发邮件、退款、删数据）一律走人工闸门
02

计划-执行 Plan-and-Execute

先出计划，再逐步执行

解决什么　先出一份完整计划，再逐步执行。把「想」和「做」分开，计划本身可以给人看、可以改，执行才不会一路跑偏。它与 ReAct 的分界只有一句：ReAct 边做边改主意，Plan 先定路线再走。

典型场景　任务大且可拆（调研报告、竞品分析、批量改造）、步骤之间弱依赖、执行耗时长需要中途确认。

失效信号　执行中频繁冒出「计划里没这一步」——任务其实是探索型的，回到 ReAct。

最佳实践

  • 计划必须是结构化清单（目标、步骤、依赖、验收标准），不是一段散文
  • 计划先落盘，最好先让人过一眼；计划错了，后面全错
  • 单步失败允许重试，整盘失败要回到「改计划」，而不是从第一步重跑
  • 每步执行完更新计划状态，别让它变成执行时没人再看的文档
  • 步数超过十步就别硬规划，拆成两段：前一段规划、后一段再规划
03

反思 Reflection / Reflexion

生成、评审、改，直到达标

解决什么　用另一轮（或另一个角色）挑错，把「一次成稿」变成「改到达标」。它有两种形态：自我反思（同一个模型看自己的输出，便宜但容易同质化）和外部评审（另一个模型、规则脚本或工具来判，贵但可信）。

典型场景　有明确质量标准的产出：格式规范、合规口径、代码规范、文案调性；也常做「生成 + 事实核查」的组合。

失效信号　每轮都在改措辞，问题却始终是同一个——评审标准太模糊，先定清单，再上循环。

最佳实践

  • 生成者与评审者分离：不同提示词、不同上下文，最好不同模型；自己评自己会同质化
  • 评审标准写成可勾选的清单，别写「请评估质量」这种空话
  • 设最大轮数与收敛条件（2 到 3 轮），否则会无限改
  • 保留每轮 diff，人能看见改了哪儿，避免越改越偏
  • 能用程序校验的（格式、字段、数值范围）别交给模型评，又快又稳
04

多智能体 Multi-Agent / Supervisor

谁干下一步，调度者说了算

解决什么　一个 Agent 扛不住时，按职责拆成多个：各有独立的提示词、工具集和上下文，由调度者分派任务、验收结果。它解决的不是「更聪明」，是上下文互相污染和工具太多挑不准。落地最常见的是 Supervisor 拓扑——调度者居中、子智能体在外围；拓扑属于架构层，第 3 节再展开。

典型场景　工具超过二十个、几类知识挤在一个上下文里打架、环节要求的角色不同（写 / 审 / 核）、可以并行拆开做的活。

失效信号　调度者的提示词比业务逻辑还长；或者子智能体之间开始来回转交、互相甩锅——说明职责没切干净。

最佳实践

  • 先问「不拆行不行」：拿掉调度者流程还能跑，就说明不需要它
  • 每个子智能体的职责一句话说得清，工具集互不重叠
  • 调度者只做分派与验收，别让它自己下场干活
  • 委派要带结构化简报：目标、约束、已完成的部分、明确不要做什么
  • 子智能体控制在 3 到 5 个；再多，调度本身就成了瓶颈
05

工作流编排 Agentic Workflow

下一步干什么，代码已经写好了

解决什么　把「哪几步、什么顺序、什么条件走哪条」写进代码或配置，模型只在每个格子里干活。它和上一张长得很像——都是多个框加箭头，差别只在箭头是谁连的：上一张由模型在运行时连，这一张在写代码时就连死了。

和普通工作流的差别　不在有没有箭头，在格子里是模型在干活，还是脚本在干活。同一张流程图，格子换成规则判断就是 RPA，换成「读懂这张发票写了什么」就是 Agentic Workflow。链式、路由、并行都是它的子形状——区别只在编排层怎么连，不在模型多聪明。

典型场景　有合规与顺序要求的流水线（解析 → 抽取 → 校验 → 成文）、入口类型混杂要先分诊、可以并行跑的批量任务。

失效信号　代码里「这一步该不该跳过」的判断越堆越多——说明流程该画成状态图了，而不是继续加 if。

最佳实践

  • 步与步之间只传结构化字段，别把上一步整段自由文本直接丢给下一步
  • 关键节点用程序校验（字段齐不齐、数值范围、引用是否存在），不要用模型自检
  • 路由必须有兜底分支，并监控它被触发的比例；分错率高于 15% 先修分类
  • 各分支共享同一套上下文格式，别每条链各写一套
  • 每步单独记 token 与耗时，才知道是哪一步变差了

真实系统通常是两三个范式叠起来用——像一道菜先焯水、再爆炒、最后勾芡，几个手法叠着来，但主手法只有一个。三个典型组合，注意每个组合里只有一个是主角，其余都是补位：

场景叠了哪几个真正决定成败的一环

反过来看，最常出事的也是这个叠法：有人把「路由 + 三个链 + 一个评审」当成一个巨大的 ReAct 循环写，结果分诊逻辑藏在提示词里、失败无法定位。范式叠起来可以，但要能画成图、对得上代码。

怎么选：只问四句

问题答案落到哪个范式
步骤固定吗固定Agentic Workflow（链式）。别上自主循环，你不需要它猜
不固定ReAct（边做边看），或 Plan-and-Execute（先定路线再走）
一次能做对吗不能Reflection，或直接上人工闸门
一个 Agent 扛得住吗扛不住Multi-Agent。工具不冲突、上下文不打架就别拆
入口类型混杂吗混杂Agentic Workflow 里的路由，记得留兜底分支
范式不分高低。链式不是「低级版 ReAct」，清蒸也不是「低级版红烧」。一个三步的流程硬上自主循环，只会让成本和不确定性白涨——本来查一次就能答的问题，变成模型自己决定查几次。
选范式只问四句：步骤固定吗、一次能做对吗、一个 Agent 扛不扛得住、入口类型杂不杂。

3从范式到架构：四种骨架P0

上一节最后那张三档图回答的是「箭头由谁画」——代码画，还是模型画。这一节往下问一层：箭头怎么连。同一档里，连法还能再分四种，而连法直接决定系统的可靠性与成本——同一道菜，一个人从头做到尾，和切配、掌勺、装盘分开做，出菜速度和稳定性完全不同。

生产里能见到的骨架只有四种，用的也是同一批零件：一次判断、一次工具调用、一次成文。变的只是它们的连法。所以判断一段代码属于哪种骨架，不要看它有几个 Agent，要看哪些箭头是写死的：写死的越多越可预期，越少越灵活。选骨架，本质是给项目在这两端之间挑一个位置。

A 单环：一个 Agent、一组工具、一个循环。最省事，也最容易失控。工具不超过十个、动作可逆、失败能重来，才适合它。要补三件事——步数上限、工具白名单、每次调用的留痕。

B 链加环：固定骨架里嵌一个自主环节。前后是写死的步骤，中间那段让模型自己决定调几次工具。大多数生产系统都长这样，也是最容易被低估的一种：它同时拿到了可预期和灵活，代价是你得自己划清「哪一段放开」。下面单独拆开看。

这张图解释了一个常见困惑：为什么明明用了模型，流程还是能复现？因为箭头在写代码时就画好了，模型只是被允许在中间那一段里多转几圈。反过来，如果整条流程只有一个大循环，那每一次跑的路径都可能不同——出了问题只能事后翻日志，不能靠重放复现。

C 路由扇出：入口先分诊，后面挂若干专才，各走各的链。适合问题类型混杂的入口，比如客服、工单。这类系统必须有一条「我不确定，转人工」——分错类的代价，往往比分诊还高。

D 编排者-工作者：一个调度者加若干执行者，调度者只做分派与验收，不亲自干活。适合职责差异大、工具超过二十个、几类知识挤在一个上下文里互相干扰。它是第四讲的主角，这里只需记住它的形状：一个不做活的节点，管着一群只做活的节点。

四种骨架不是并列选项，是升级路径

新手最容易犯的错，是一上来就想画 D。实际上骨架该跟着信号走：撞到哪个问题，才升到下一档。没撞到就升，等于给三轮车装飞机引擎。

撞到这个信号该跳到为什么
同一个工具被反复调错，步数经常顶到上限B 链加环把前后固定下来，只留中间一段放开，路径就收敛了
一条链上的 if 超过五条，还在继续长C 路由扇出不是分支太多，是入口没分诊；分段之后每条链都变短
工具超过二十个，或几类知识互相干扰D 编排者-工作者上下文塞不下才是拆角色的理由，不是「听起来更先进」
反过来：一共就三步，且每步都不会失败不要骨架写成一串函数调用就行，加循环只会加不确定性

一张生产架构要有五个位置

不管最后落在 A 还是 D，一个能上线的架构里都该有这五个位置。它们不是流程的五个步骤，而是五个职责——缺哪个，就会在对应的场景里翻车。

位置它干什么常用范式缺了会怎样
入口分诊判断这是什么请求，该走哪条路工作流编排 Agentic Workflow所有请求走同一条路，专才的优势全没了
执行真正查数据、调接口、动文件工作流编排 / ReAct
Agentic Workflow / ReAct		只会聊天，不会动手
质检输出前按标准过一遍反思 Reflection错的结果直接就发出去了
闸门不可逆动作前停下来等人人工介入 Human-in-the-loop一次误发邮件、一次误退款，赔掉一个客户
状态与留痕存流程位置，记每次调用检查点 + 链路追踪
Checkpoint + Tracing		崩了从第一步重来，错了查不到是哪一步

注意最后一行不属于任何范式，它横跨所有范式。这也是新手最容易漏的一层：范式和骨架都能画得很漂亮，但状态只存在进程内存里，一次发版就全没了。

架构不是把五种做法全塞进一个循环，是回答三个问题：状态存在哪、失败怎么退、谁最后签字。三个问题答不上来，那张图就还只是示意图。
先数箭头：哪些必须写死，哪些必须放开。写死的越多越稳，放开的越多越活——骨架就是这条线上的一个位置。

4框架这一层：三层对齐P0

范式决定怎么想，骨架决定谁在哪，框架决定少写多少行。前两节把前两个说完了，这一节把它们对到具体框架上：每个框架默认搭出哪种骨架、最顺手接哪种范式。看懂这层对应，你就能反过来检查自己的判断——如果你定的骨架和选的框架默认形状不一样，那么接下来每一行代码都在跟框架较劲。

逐个项目的定位、技术栈、真跑起来会撞到什么，留给第三讲。这里只做对应。

先分清三层，否则等于把三种东西放在一张榜上比价

网上很多「框架对比」是假对比：把一个库、一个装好就能干活的运行时、一个厂商托管的平台排在一起打分。它们的运维责任根本不在一个量级，分数没有可比性。

层是什么代表你还得自己负责什么
框架 / 库写代码时调用的依赖，跑在你的进程里LangGraph、CrewAI、Pydantic AI代码、部署、安全、升级、评测
运行时装好、接上模型和工具就能干活的成品 AgentOpenClaw、Hermes Agent 这一类机器、更新、模型密钥、备份、访问控制
托管平台厂商替你跑那个循环，你只交配置和数据Claude Managed Agents、Microsoft Foundry、Dify 云版配置、喂进去的数据、账单

三层的关系可以用一句话记住：越往下，你要管的越少，能改的也越少。这一节说的全是第一层——只有这一层由你决定骨架。

范式 → 骨架 → 框架：一条线串下来

把三节的内容叠在一张图上，就是下面这张。左边是你判断出来的做法，中间是它要求的形状，右边才是能承接这个形状的框架。顺序不能倒：从右往左推，等于让工具的默认值替你做设计。

这张图还解释了一个常见困惑：为什么 LangGraph 在四行里出现了三次，却依然有人用它写了半年还是在写 if-else？因为它不提供默认骨架——节点和边都由你画，画成什么样就是什么样。相反，CrewAI 只出现在最后一行，因为它的抽象就是「角色 + 任务」，你很难用它写出一个单环。

框架的默认形状，会悄悄变成你的架构。这不是框架的错，是选型时没对齐。所以顺序永远是：先认范式，再定骨架，最后才在对应那一行里挑名字。

问偏向「重」的那一侧落到哪

谁维护它、维护多久就一个人，最多半年越薄越好；重框架会先变成维护负担

三个都答「不」的时候，答案通常不是「选个最轻的框架」，而是不用框架——一个朴素循环，配一个工具调用能力足够强的模型，能覆盖相当多的场景。两个小菜不必先建一座中央厨房，复杂度真上来了，整套厨具才值那个价。

两条反常识，能砍掉一半错误的冲动。一是框架不如模型：强工具调用的模型配朴素循环，常常打赢弱模型配精巧的图。二是开源自托管不等于安全：2026 年 4 月某开源 Agent 运行时连爆四个高危漏洞、最高 CVSS 9.6，其中绝大多数受害者是「我自己部署的，数据在自己手里」。私有化是入场券，不是合格证。
从这里往哪走，两条路都行。想先看货架上有什么，去第三讲：三十多个项目按档位摆开，每个都写了定位、场景、技术栈和止点。想先把结构定死再动手，等开工之后，拿自己项目的流程回来走一遍左边的三列——那时你手里的信息，比现在多得多。

5小结：一条顺序，五个判断P1

这一讲没有让你记住任何一个框架的名字，只给了一条顺序：先认范式，再定骨架，最后才挑名字。顺序反了，选型就退化成比功能表。五个判断，每句后面附一句「它在实际里怎么体现」。

01
三个词各答一个问题

范式答「这类问题怎么想」，架构答「谁按什么顺序干」，框架答「谁来提供这套零件」。三者是三个层次的提问，不是同一种东西的三种叫法。

「我们用了 LangGraph」不是方案；「一张带检查点的图，模型只在两个节点里判断」才是方案。

02
五种范式，各治一种病

ReAct 治「不知道下一步该调什么」；Plan-and-Execute 治「步骤多但能预估」；Reflection 治「一次做不对」；Multi-Agent 治「需要不同视角互相挑错」；Agentic Workflow 治「必须可复现」。没有一种全能。

记住这条就能省掉一轮纠结：反思和计划-执行几乎从不单独成为选型理由——一个是环里多调一次，一个是链的前半段。

03
四种骨架，分界只有一条

哪些箭头是写死的。写死越多越可预期，越少越灵活；升级靠撞到信号，不靠个人喜好。

同一个工具反复调错才上「链加环」；分支超过五条才上「路由扇出」；工具超过二十个才上「编排者-工作者」。

04
框架的默认形状会变成你的架构

所以选型不是比功能表：先定站哪一层（库、运行时、托管平台），再看它默认搭哪种骨架、最顺手哪种范式。你看中的是它的默认值，不只是它的功能。

LangGraph 在对应图里出现三次，不是它最强，是它不替你决定形状——画成什么样就是什么样。

05
很多时候，最优解是不用框架

不用续跑、不用人签字、一个人维护半年——三个问题都答「不」，就该写一个朴素循环，配一个工具调用足够强的模型。

两个小菜不必先建一座中央厨房；复杂度真上来了，整套厨具才值那个价。

这一讲给的是顺序，下一讲给的是货架。第三讲把三十多个项目摊开，每个写清定位、场景、技术栈。你会发现自己看它们的方式变了：先找骨架，再看名字——而不是反过来。
顺序比结论重要：先认范式，再定骨架，最后才在对应那一行里挑名字。
