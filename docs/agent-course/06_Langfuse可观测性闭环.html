可观测性：让每一步都留下证据

Agent 出故障的时候，日志只会告诉你「它挂了」，很少告诉你「它在第几步、因为什么挂的」。真正能救命的，是把一次请求还原成一棵能点开的树；再往上，是把这些树变成一组能重复跑的题。

1两种问法，两种工具P0

场景先摆出来：用户昨天问了一句「我这种情况能不能报销」，系统答得头头是道，但答错了。今天要你给一个解释。

这时候你会问出三个不同的问题，它们需要三种不同的证据：

问法你要的证据对应工具
有没有出事哪个用户、什么时间、哪个接口、状态码多少结构化日志
死在哪一步这次请求的完整调用树：每步的输入输出、耗时、花了多少钱链路追踪
是不是变坏了同一批题重跑一遍，分数比上次掉了几何评测

第一种问法日志就能答。麻烦的是后两种——尤其是 Agent 这类系统，最常见的故障形态是什么都没报错，但答案是错的。没有异常、没有 500、日志里一行红字都没有，你说它挂了都不成立。

错误藏在语义里，而语义不在日志的字段里。这就是为什么「有日志就够了」在 Agent 项目里特别容易翻车：日志是按事件写的，而问题出在链路上。

日志回答「有没有出事」，追踪回答「哪一步出的事」，评分回答「这次改动是不是变坏了」——三者不能互相替代。

2四个概念，一句话一个P0

Langfuse 的数据模型不复杂，但一开始搞混「追踪」和「节点」，后面所有统计都会对不上。这四个概念是层层包含的关系：

概念是什么典型用途
Session 会话一段连续对话。多轮之间的追踪都挂在它下面，靠 session_id 串起来「这个用户整段对话里发生了什么」
Trace 追踪一次请求 = 一棵树。有输入、输出、总耗时、总花费「这一问为什么答错」
Observation 节点树上的一个节点。分四类：span、generation、event、tool「检索花了多久、召回了什么」
Score 分数挂在某棵树或某个节点上的一次评价，可来自人工、规则或模型「这次的回答合格吗」

只有 generation 会算钱

节点四类里，成本与 token 只统计 generation。如果你把一次模型调用记成了普通 span，界面上就会出现「有调用、但花费为 0」的怪现象——报表看不出问题，账单却对不上。

反过来的坑同样常见：把检索、工具调用也记成 generation，成本会被虚高一截，因为你把「数据库查询」也算成了「模型推理」。

判断口诀：要花钱的那一步记 generation，不花钱但要看耗时的记 span，纯时点标记记 event。这条规则贯穿整套报表的可信度。
会话装追踪、追踪装节点、分数挂在节点上；只有 generation 算钱，记错这一点，后面所有报表都是错的。

3三个接入点，三个必须写对的键P0

接入的工程量比想象中小，但要接对位置。三处就够：

位置挂什么不挂会怎样
请求入口会话 ID、用户 ID、标签。挂一次，整条链路继承每个节点都得手动补，漏一个就断链
图与链的节点自动生成：模型调用、工具调用各成一节只剩一棵光秃秃的根节点，看不到内部
业务关键步骤手动开 span，补业务语义：召回几条、命中哪个策略技术上有记录，但解释不了业务上为什么错

第三处最容易被跳过，也最值钱。检索召回了 0 条这件事，框架不知道，只有你的业务代码知道。多写五行，排查时省两小时。

入口挂一次：包住整段被追踪的逻辑

# app/api/v1/chatbot.py —— 在请求入口挂一次，图里所有调用自动继承
with trace_attributes(session_id=session.id, user_id=str(session.user_id), tags=["chat"]):
    result = await agent.get_response(...)

这个上下文管理器做的事情很朴素：把会话、用户、标签写进当前调用上下文，之后创建的每个节点都带上它们。它还有个省事的设计——你没传的字段，会自动去请求上下文里取，而那里已经被日志中间件绑过一次。同一份上下文，日志和追踪共用，不用传两遍。

三个键，写错等于没接

这是接入阶段最高频的坑，而且症状很隐蔽：追踪列表里明明有数据，但「会话」页是空的、按用户筛不出东西、成本按用户统计全是零。

你以为的写法实际生效的键写错的症状
session_idlangfuse_session_id追踪有数据，会话页空空如也
user_idlangfuse_user_id按用户看成本、看延迟，永远是空的
tagslangfuse_tags标签筛选失效，没法按环境分组

Langfuse 的 LangChain 集成只认这三个带前缀的键，其余键一律当普通元数据存着，不会提升成追踪级属性。项目里的写法是这样的：

# 业务自用的键照写，同时补上带前缀的三兄弟，两套并存不冲突
"metadata": {
    "user_id": user_id, "session_id": session_id,        # 日志用
    "langfuse_session_id": session_id,                   # 追踪用
    "langfuse_user_id": user_id,
    "langfuse_tags": ["chat", settings.ENVIRONMENT.value],
},
"run_name": "chat",   # 不设，界面上所有追踪都叫 LangGraph

还有两个次要但会让人怀疑人生的坑：

  • 命令行脚本不 flush 就退出——追踪数据在缓冲区里，进程一退全丢。服务进程常驻看不出来，脚本一跑一个空。项目里封装了 flush()，脚本末尾调一次。
  • 拿中文昵称当用户 ID——追踪属性要求 US-ASCII 且不超过 200 字符，中文会被静默丢弃。ID 用主键，昵称放元数据。
一条自检命令省半天：make trace-smoke 会造一条探针追踪、强制上报，并打印直链。先证明「key 通、数据到」，再去查业务代码——顺序反了，你会同时怀疑三件事。
入口挂一次、节点自动生、业务步骤手动补；三个带 langfuse_ 前缀的键写不对，接了也等于没接。

4云端还是自建：先算清要几个容器P1

这件事没有悬念式的答案，只有两种代价。先把账摆开：

方案代价适合谁
云端免费版每月 5 万 units，数据留 30 天，2 个成员，摄入上限 1000 请求/分自用到小团队验证，数据不敏感
云端付费版每月 29 美元起，10 万 units，数据留 90 天，成员不限团队协作，不想碰运维
自建六个容器：Web、Worker、Postgres、ClickHouse、Redis、MinIO；约 2 GB 内存；升级、备份、证书全归你数据不能出内网，或要长期留存

注意自建的复杂度不在「跑起来」，在「跑得久」。文档里写得很直白：事件先落对象存储，再由后台进程灌进 ClickHouse；这意味着出事的时候，你要会看四个中间件的状态，而不只是一个日志文件。

项目里给了一套可直接起的最小实现：make langfuse-up，端口全部避让开发栈，起来后浏览器开 localhost:3010 建组织、拿 key、填进 .env，然后 make langfuse-down 随时收工。

版本对齐：SDK 与服务端不要一个 3.x 一个 4.x 硬凑。上传协议仍在演进，跨大版本混搭的典型症状是「界面能看到追踪，但成本字段是空的」——这种问题极难查，因为它不报错。
自建的成本不在钱，在「谁来养 ClickHouse」；数据不出内网才自建，否则先用云端免费额度把它用起来。

5可视化：什么该自己写，什么不该P0

这个问题可以直接给结论：追踪树永远不要自研，业务报表才值得自己写。

理由不在于「写不出来」，在于投入产出比悬殊。一个能用的追踪界面要做：树状渲染、按属性检索、多次调用对比、分享链接、权限、大字段截断、以及背后那套列式存储的查询优化。这不是一个页面的工作量，是一个产品的工作量——而它已经被做完并且开源了。

你要看的东西谁在看用什么自己写吗
某次请求的调用树、每步输入输出工程师查故障Langfuse 界面不写
吞吐、错误率、P95、资源占用值班 / 运维Prometheus + Grafana（compose 已编排）不写
成本、会话量、质量分数趋势你、主管、周报先用界面自带看板，再补一个命令行报表只写薄壳
和业务数据联查（订单、课程、报名记录）业务方自己的查询 + 已有 BI写，但只读

为什么「只写薄壳」是更好的选择？因为聚合类需求变化太快：今天要看日成本，明天要看单会话成本，后天要看某个工具的错误率。这类需求用一张命令行表格几行代码就能改完，做成前端页面就变成一次排期。

落到项目里：一张终端报表

按上面的判断，这个项目里唯一自己写的可视化是一张命令行报表：拉最近一段时间的追踪，压成三张表——总量与钱、按天趋势、最贵的几条。

make trace-report                 # 最近 24 小时
make trace-report HOURS=168       # 最近 7 天

输出（节选）：
① 概览    trace 数 128 ｜ 会话 31 ｜ 总成本 $0.4218 ｜ P50 2.1s ｜ P95 6.8s
② 按天    11-05  42 条  $0.1320  P95 5.9s
③ 最贵    11-07 14:22  s-8f3a  8.4s  $0.0182  「我这种情况能不能报销」

它只做三件事：拉数据、聚合、打印。没有数据库、没有前端、没有缓存。要加一个「按工具统计错误率」，仍然是加三十行代码——这就是「薄壳」的意思。

最常见的浪费：先自研一个追踪列表页，做到第三周才发现还缺搜索、还缺按会话聚合、还缺分享给同事看，最后要么推倒，要么把现成的又抄一遍。
自研的边界画在聚合上，不要越到渲染上；追踪树用现成的，周报用命令行，两者中间隔着一整套产品的工作量。

6把追踪接进评测：让「变好了」可以证伪P1

追踪解决「这一次为什么错」，评测解决「这一版是不是真的比上一版好」。前者是点，后者是面，缺一个都只能靠感觉。

把两者接起来的机制只有一句话：分数必须回写到产生它的那条追踪上。回写到别处（表格、文档、聊天记录），“改完感觉好了”就永远无法证伪。

项目里已经有一套跑通的实现：拉最近 24 小时里还没被打分的追踪，按指标逐条打分，再把分数写回原追踪。

# evals/evaluator.py —— 拉未打分的追踪，逐条评分后回写
traces = langfuse.api.trace.list(
    from_timestamp=datetime.now() - timedelta(hours=24),
    order_by="timestamp.asc", limit=100,
).data
pending = [t for t in traces if not t.scores]     # 打过分的跳过，省评测额度

langfuse.create_score(
    trace_id=trace.id, name=metric["name"],
    data_type="NUMERIC", value=score.score, comment=score.reasoning,
)

两个细节值得抄：先过滤掉已有分数的，否则每次重跑都在同一个样本上烧钱；把理由写进 comment，否则三个月后你只知道它 0.2 分，不知道为什么。

最低配的起步方式：先只做一个指标（比如「回答是否基于检索内容」），二十分题，二十条基线。这个规模的题集就能挡住大多数「改完感觉变好了」的自我欺骗。
分数必须回写到产生它的那条追踪上；题集从线上低分样本里长出来，别坐在屋里想。

7五步验收与排错表P0

动手练习

按顺序做完这五步，做完就能排查了

  • ① 配 key：云端建项目拿 pk-/sk-，或本地起一套；写进环境文件，跑 make trace-smoke，能打出直链才算通。
  • ② 发一次真实对话：界面上出现一条 chat，点开节点不少于三个（记忆检索、模型调用、可能的工具调用）。
  • ③ 看会话页：能按会话把它们串起来。串不起来，就是归因键没写对。
  • ④ 看成本：不是 0。是 0 就说明模型调用没被记成 generation。
  • ⑤ 故意制造一次错误：随便让某个工具抛个异常，确认能在界面上按 ERROR 筛出这一条，并看到异常文本。

做完再加一步：把某条答错的追踪挑出来，给它打一个分数，然后去题集里找它。走完这一圈，闭环就通了。

排错顺序很重要：先证明「上报链路通」，再证明「上下文挂对了」，最后才怀疑业务代码。反着来，你会同时怀疑三件事，然后一件都定位不了。
先跑自检证明链路通，再查归因键，最后才看业务代码；顺序反了，三件事一起怀疑，一件都查不出来。
