主流 Agent 开源框架与产品

星数、许可证、技术栈按 2026 年 11 月各项目公开仓库与官方文档整理。这类项目两三个月就换一版，星数只能当量级看——真正稳定的是它站在哪条路线上，以及技术栈决定了它擅长什么。

1四条路线：这批项目各站哪一档P0

把三十多个项目摊开，第一反应是「太多了，没法比」。但比不下去的原因，往往是拿不同档位的东西在比：有人问「Dify 和 LangGraph 哪个好」，就像问「成衣和缝纫机哪个好」——它们解决的不是同一个问题。

分档只问一句话：这条链，是它替你装好了，还是等你来装。问完，四档自然出来，投入从「填几个表」一路加到「每行都自己写」。

第一档

装好就用

产品形态是「一个一直在的助手」，你通过聊天窗口跟它说话，不写代码也不画图。你改不了它的形状，只能决定给它什么权限。

第二档

画布搭

它给你一个界面，你在里面拼节点、传文档、连模型，拼完能发布成 API 或嵌入页面。改得动，但只能改它允许你改的部分。

第三档

写，但看得见

要写代码，但自带一个可视化调试台，能看见每一步的输入输出和状态。介于「纯代码」和「画布」之间，是调试体验最好的一档。

第四档

纯库

装进来就是一堆函数和类。没有界面、没有存储、没有日志，所有东西你自己接。控制力最强，前期成本也最高。

为什么按这个维度分，而不是按星数排。星数只说明「有多少人收藏过」，不说明它适合干什么。按投入分档，你看到任何一个新项目，三十秒内就能把它塞进某一档——这比记住三十多个名字有用得多。

还有一个维度不在这个谱系里：它服务谁。同一档里，有的想做所有人的底座，有的只服务一个行业。档位决定你能改多深，行业决定它替你加装了什么——第五节的二十个项目就是从「服务谁」切进去的。

先判档位，再比功能。跨档比较得出的结论，基本都是错的。

2平台型：六个平台，差别在「默认形状」P0

六个平台放在一起，功能列表高度重合：都有知识库、都有工作流画布、都接几十个模型、都能发布 API。真正拉开差距的是它默认把你往哪个形状上带——你打开界面第一眼看到什么，决定了你后面会自然而然做成什么。

先看一眼这类项目共同的骨架。它们的技术栈几乎是一个模子：一个 Web 服务收请求，一个异步队列干重活，一个关系库存配置，一个向量库存知识，一个前端画布负责编排。

DifyApache-2.0 · open-core159.7k
定位
LLM 应用平台。把 RAG、工作流、Agent 三种应用形态放进同一个工作区，画完能直接发布成 API 或嵌入页面。
场景
一个团队要同时维护好几个 AI 应用，且改流程的人不一定是工程师；或者需要对外提供接口给业务系统调用。
技术栈
Python 3.11+ / Flask + Celery + SQLAlchemy
PostgreSQL + Redis + 向量库（30+ 适配）
Next.js + React + ReactFlow
自研 DAG 引擎 graphon，Nginx，Compose 七个容器起
止点
open-core，企业版功能不开源；容器多，机器不能太小。
MaxKBGPL-3.023.1k
定位
企业级智能体平台，走的是渐进路线：先做知识库问答，再上工作流，最后到 Agent。不逼你一上来就搭复杂流程。
场景
内部制度问答、客服知识库；要零代码嵌进企业微信 / 钉钉 / 飞书 / 公众号这类已有系统。
技术栈
Python / Django + Vue 3
PostgreSQL + pgvector
内建 LangChain 做检索链与工具调用
单容器 :8080，全部数据落一个卷
止点
GPL-3.0 有传染性，集成进闭源产品要谨慎；默认管理员密码必须改。
n8nfair-code（非 OSI）208.8k
定位
工作流自动化工具，不是 Agent 平台。它的主场是「系统与系统之间」的搬运和触发，AI 只是其中一类节点。
场景
定时同步数据、Webhook 触发、把 CRM / 邮件 / 表格串起来，中间插一段模型判断或摘要。
技术栈
TypeScript / Node.js
前端 Vue
SQLite（默认）或 PostgreSQL
单容器 :5678
止点
许可是 Sustainable Use License，不是 OSI 意义上的开源；复杂 Agent 逻辑塞进来会很别扭。
LangflowMIT~47k
定位
LangChain 的可视化外壳。画布上每个节点背后都是一个 LangChain 组件，画完可以把代码导出带走——这是它和其他画布最大的区别。
场景
想先画着看效果、再拿代码去改；或者用它做演示，让人一眼看懂链路。
技术栈
Python + LangChain
React 前端
单容器 :7860
组件库 150+ 节点

图一复杂，画布比写代码还慢；导出的代码仍需工程化才能上生产。
FlowiseApache-2.053.5k
定位
Langflow 在 Node 生态的对照物，基于 LangChain.js。定位同样是低代码搭 chatbot 和 RAG 流程。
场景
团队本身是 JS / TS 栈，部署在 Node 基础设施上；不想为了一个画布再养一套 Python 环境。
技术栈
Node.js / TypeScript
LangChain.js
React 前端
单容器 :3001，镜像约 600MB

Python 侧的模型与工具生态更全，这边会慢半拍。
RAGFlowApache-2.093.7k
定位
不做「应用平台」，只把知识这一层做到极致。核心是 DeepDoc：扫描件 OCR、复杂版面分析、表格结构还原。
场景
合同、标书、研报、病历这类 PDF——普通按字数切块答出来全是错的，必须先把版面读懂。
技术栈
Python / Flask（API）+ Go / Gin（高吞吐服务）
DeepDoc：OCR + 版面 + 表格，ONNX Runtime / spaCy
Elasticsearch（默认）/ Infinity / OpenSearch / OceanBase
MySQL 8 + MinIO + Redis + NATS
React 18 + Vite；litellm 接模型；gVisor 跑代码
止点
吃资源（4 核 16G 起步）；解析慢，文档一多要排队。
六个里最容易选错的是 n8n。它星最多、教程最多、看起来最能干，但它不是 Agent 平台。把「要推理、要迭代、要判断」的活塞进 n8n，你会发现节点越连越乱，最后变成一个没人敢改的巨型流程图。
平台型的差别不在功能列表，在默认形状：Dify 让你做成应用，MaxKB 让你做成问答，RAGFlow 让你先把文档读懂，n8n 让你把系统接起来。

3助手型：四个「装在自己机器上」的常驻者P0

上一节的六个平台，产品逻辑是「你做一个应用给别人用」。这一节的四个反过来：它本身就是一个用户，替你去操作东西。你不需要搭流程，你需要给它权限，然后跟它说话。

它们的结构也完全不同——没有画布，只有一条常驻的循环，外面挂一圈渠道和工具。

OpenClawMIT393k
定位
跑在自己设备上的个人 AI 助手，通过聊天软件交互。星数最高的 Agent 项目，也是「助手型」这个品类的定义者。
场景
全天在线的私人助理：收邮件、排日程、盯网页变化、跑脚本；你在手机上发一句话，它在服务器上做完。
技术栈
TypeScript / Node.js，MIT
官方 Docker 镜像，也支持 npm 装
22 个聊天渠道适配；专用 Chrome 做浏览器控制
持久记忆 + ClawHub 技能市场（700+）+ REST API
止点
权限开太大风险高（可读写文件、跑 shell）；迭代极快，破坏性变更常有，issue 积压近万。
Hermes AgentMIT199k+
定位
Nous Research 出品，主打自我进化：任务做完会把过程沉淀成一个 skill，下次遇到同类活直接调，而不是重新想一遍。
场景
长期重复的个人工作流——你希望它越用越顺手，而不是每次从零开始解释。
技术栈
Python 3.14，Debian 13.4 基础镜像
s6-overlay 做进程守护；Docker 单容器
gateway 模式暴露 OpenAI 兼容 API(:8642) + dashboard
6 种终端后端：本机 / Docker / SSH / Daytona / Singularity / Modal
内置 Chromium + Playwright
止点
单用户设计，没有多租户；学到的技能质量取决于模型水平。
Agent ZeroMIT19.8k
定位
「给 Agent 一台完整的电脑」。容器里带一个 XFCE 桌面，它能像人一样操作真实 GUI 软件。
场景
要跨桌面应用完成任务的实验场景；或者想研究「一切皆 prompt」这种极端设计。
技术栈
Python；Docker 单容器（agent0ai/agent-zero）
容器内 XFCE + 浏览器 DOM 标注 + LibreOffice
行为全部写在可编辑的 prompt 文件里，不是硬编码
插件 Hub（100+）+ MCP

无限制 shell 访问，安全风险高，只能隔离跑；无多用户、无 RBAC、无审计。
DeepSeek HarnessMIT · 预览版272k
定位
DeepSeek 官方的 Agent 运行器（harness）：桌面应用或本地网页工作区，模型在里面改文件、跑命令、装插件。「一切皆插件」是它的架构主张。
场景
编码任务；更适合作为「一个 harness 怎么设计」的参考实现来读。
技术栈
TypeScript；底层 Cordis 插件框架（有 arXiv 论文）
Electron 桌面（mac / Win）+ npx @deepseek-ai/dsh web(:3080)
Node 24.9+；模型适配走 pi-ai，可接非 DeepSeek 模型
三层沙箱：Linux bubblewrap/Landlock、macOS Seatbelt、Windows 受限令牌
止点
developer preview。官方明确写：未做安全审计、不能当生产用。出过 CVE-2026-82533 沙箱逃逸（9.4 分）。桌面版没有 Linux。
这一档必须记住的一句话：能力和风险是同一件事。它之所以能替你干活，正是因为它能读文件、跑命令、点按钮。dsh 那个 CVE 的成因很典型——本地网页界面信任了请求头、又没鉴权，被注入的文本就能诱导 Agent 把自己的沙箱关掉。装这类东西，第一件事不是配模型，是确认沙箱和权限。
平台型你是在造一个应用，助手型你是在雇一个同事——雇人要先划权限，不是先看能力。

4编排库：七个库，三种心智模型P0

这一档装进来就是一堆函数和类，跑在你自己的进程里。听起来都差不多，但它们在怎么描述「下一步干什么」这件事上，走了三条完全不同的路。选错心智模型，写起来会一直别扭。

LangGraphMIT44k
定位
把 Agent 写成状态图：节点干活，边决定下一步，整张图能暂停、存档、恢复。生产环境里最经得起查的一档。
场景
流程里有循环、分支、重试、人工审批的长任务；出问题时需要精确知道停在哪一步、状态是什么。
技术栈
Python / JavaScript
pip install -U "langgraph-cli[inmem]" → langgraph new → langgraph dev
起 API(:2024) + LangGraph Studio 可视化调试台 + 热重载
checkpoint 可落内存 / SQLite / PostgreSQL；langgraph up 才需要 Docker
止点
学习曲线在七个里最陡；写起来啰嗦——但那份啰嗦换来的是可审计。
它是最值得先跑一遍的一个。因为 langgraph dev 起的不只是接口，还有一个可视化界面：你能看见每一次节点跳转、每份状态快照。前面那些画布类项目让你看见「流程长什么样」，这个让你看见「这一次它到底走了哪条边」——后者才是调试真正需要的。第二天项目的主栈就是它。

编排库选的是心智模型，不是功能表：图、角色、交接，三条路各自解决不同形状的问题。

5垂类：一个行业，一套打法P0

前面三类都想当「底座」——一个平台服务所有场景。这一类反过来：只服务一个岗位，把那个岗位的脏活全接过去。它们通常不是拿来搭应用的，是直接拿去干活的。

垂类强，不是因为模型更强。同一个 agent loop，套上三层加装就完全不是一回事：领域语料（法规、病历、研报、运维手册）、行业连接器（HIS、法院、交易所、K8s、ERP）、行业验收标准（引用可溯源、数字可复算、建议能签字）。

四个值得拆开看的

表里最容易被当成「同类」的这四个，其实各自解决一种不同的问题：组织分工、证据链、口径统一、引用溯源。看懂这四种壁垒，再看别的垂类项目就有坐标系了。

TradingAgents金融120.4k
壁垒
把投研拆成四类分析师 + 多空辩论 + 风控 + 基金经理，每个角色只拿自己那份材料。价值不在猜得准，在过程能复盘——谁看多、谁反驳、依据哪条数据，全留痕。
场景
研究「多智能体怎么分工」的最佳样本；或者要给投研流程做一个可解释的骨架。
止点
官方自己写明只做研究：有前视偏差、输出不确定、一次分析要几十次模型调用。别接实盘。
HolmesGPT运维3.8k
壁垒
它做的是调查，不是总结。从一条告警出发，自己去查 K8s、Prometheus、日志、云 API，把证据链摆出来。CNCF Sandbox，默认只读。
场景
告警太多、值班的人只会照手册点；想让机器先跑一遍「到底哪儿坏了」。
止点
只读是默认值，也是正确值。让它改生产，先得有回滚和审批。
Wren AI数据分析18.1k
壁垒
不直接让模型写 SQL，先建语义层（MDL）——把「营收」「活跃用户」的定义写在模型外面。模型只在这层之上生成 SQL，数字才对得上账。
场景
指标口径老吵架、BI 报表和业务对不上数。
止点
语义层没覆盖的问题它答不了，会老老实实失败。这比编一个答案好，但也就到此为止。
PaperQA2科研8.4k
壁垒
把引用当一等公民。检索 → 重排 → 逐段总结 → 成文，每个结论都指到具体论文的具体段落。
场景
文献综述；需要逐句溯源的合规、医学、政策问答。
止点
只认科学文献。通用办公文档用 RAGFlow 更合适，别硬套。
法律和医疗是最热的两条赛道，也是开源项目最难直接用的两条。这两个方向的开源项目普遍停在千星级，而且多是「某国法规」或「某家医院」的定制版。卡点不在技术，在数据拿不到、责任担不起：法规库要授权、病历不能出院内。所以在这两个方向，真正的壁垒是连接器与合规流程——先解决「怎么合法拿到数据」，再谈模型。
垂类的护城河不在模型，在「它接好了哪个系统、认哪套口径、出错谁负责」。

6同一件事，三条路：一次对照P0

前面四节是横向铺开。这一节竖着切一刀：拿一件最小的活——一份 PDF 变成能问答的东西——在三条路上各做一遍，看步数、看你能改什么、看它在哪里顶住。

维度平台路（MaxKB / Dify）画布路（Langflow / Dify 工作流）代码路（LangGraph）

停一下

用你自己的需求，走一遍这张表

先别急着选工具。拿你手上真实的那个流程，回答两个问题：

  • 这条流程里，有没有哪一步必须停下来等人确认？
  • 有没有哪一步走不通要退回去重来？

两个都答「没有」，平台路就够，而且是最省事的。答「有」任何一个，画布就开始别扭；两个都有，直接写代码——否则你会在画布上花更多时间绕开它的限制。

这一节没有让你动手装任何东西。对照表本身就是要带走的东西：下次有人跟你推一个平台，你就问这两句。
三条路都能把 PDF 变成问答，区别在「第三步之后你还能不能改」。

7换血与三个陷阱P0

这个领域的名单每半年换一批。2024 年数得出四十来个「框架」，到 2026 年真正有社区规模的不到十个。所以看这份清单，除了记住谁在，更要记住为什么会有人掉队。

陷阱一：星数当健康度

星数只涨不跌，一个八千星、半年没提交的项目，看上去比一个两千星、天天在提交的项目健康得多。真正要看的三个信号：最近三个月有没有提交、issue 有没有人回（不是有没有被提）、背后是个人账号还是公司 / 基金会。

陷阱二：三种「开源」不是一回事

许可类型代表对你的实际影响
真开源MIT / Apache-2.0：LangGraph、CrewAI、OpenClaw、MaxKB(GPL)随便改、随便商用。GPL 有传染性，集成进闭源产品要单独评估
fair-coden8n源码可见、可自托管，但对「拿它做成竞品对外卖」有限制，不是 OSI 定义的开源
open-coreDify核心开源，企业功能闭源。你能改的只是它愿意开源的那部分

「开源」这两个字在选型文档里经常被当成一个二元属性，实际是一条谱：能读代码、能改代码、能拿去卖，是三件不同的事。

陷阱三：把预览版当产品用

dsh 是最典型的例子：27 万星、官方出品、架构漂亮，但仓库里明写着 developer preview，代码没做过安全审计，还出过一个 9.4 分的沙箱逃逸。这类项目拿来读、拿来学、拿来在隔离环境里试都对；拿来接真实业务，就是把风险直接搬进生产。

还有一个容易被忽略的变化：MCP 把工具层拉平了。以前换个框架，所有工具封装都得重写，这是最大的锁定成本。现在把工具做成 MCP server，LangGraph、CrewAI、AutoGen、OpenClaw 都能直接接。锁定成本一降，比的就只剩编排质量和可调试性——这也是为什么这一层正在快速收敛。
看一个项目能不能用，别问「多少星」，问「上一次提交是什么时候、issue 有没有人回、谁在为它负责」。

8怎么选：三问锁定方向P0

三十多个项目不可能都试一遍。实际选型时，三个问题基本就能把范围缩到两个以内。

第几问问题答案指向
第一问这条流程里有没有「停住等人」或「退回重来」？有 → 代码路（LangGraph）；都没有 → 平台路就够，别自我加难度
第二问以后改它的人是谁？业务岗也要改 → 平台路；只有工程师改 → 代码路；两边都要 → 平台做外层、代码做内核
第三问你现在的难点在知识质量，还是在流程控制？知识不准 → 先解决解析与检索（RAGFlow / MaxKB）；流程绕不清 → 先解决编排（LangGraph）

按需求直接对号

要问答

文档进、答案出

普通文档选 MaxKB（单容器最省事）；扫描件、复杂版面选 RAGFlow（先把版面读懂）。

要流程

多个系统串起来

n8n。它不擅长推理，但擅长触发、重试、把结果搬到下一个系统。

要产品

对外提供 API 的应用

Dify。三种应用形态齐、发布链路完整，代价是 open-core。

要控制

流程复杂、要审计

LangGraph。写起来最重，但每一步都能查、能停、能续。

要助手

给自己配一个常驻的

OpenClaw（渠道最多）或 Hermes（会自己攒技能）。先在隔离机器上跑。

要行业

直接干某个岗位的活

编码看 OpenHands、运维看 HolmesGPT、数据分析看 Wren AI、科研看 PaperQA2。它们不通用，但替你接好了行业系统。

9小结：看完三十多个名字，带走五个判断P1

这一讲摊开了三十多个项目，但没有一个需要你现在就装。真正要带走的是定位一个项目的方法：先把名字放回它那个抽屉，比较才有依据。

01
四档不是四种技术，是四种「谁来装」

装好就用、画布搭、写代码但看得见、纯库。档位决定你能改多深、要付多少维护成本，技术本身反而差别没那么大。

跨档比较得出的结论基本都是错的：拿 MaxKB 和 LangGraph 比「谁更强」，等于拿电饭锅和灶台比。

02
平台型的差别只在「默认形状」

Dify 强在编排，RAGFlow 强在解析（DeepDoc 先读懂版面），MaxKB 强在单容器，n8n 强在触发与连接，Langflow 强在画完能把代码导出带走，Flowise 强在 JS 栈直接可用。

功能表都差不多，差的是它默认把你带到哪种应用形态；选了平台，等于选了那个形状。

03
编排库的差别只在「谁决定下一步」

画图（LangGraph）、分岗位（CrewAI）、交接（Agents SDK），加上一个正在换血的对话派（AutoGen → Microsoft Agent Framework）。

心智模型选错，写起来会一路别扭：补丁越打越多，最后成了「用图框架写角色协作」。

04
垂类的壁垒不在模型，在三层加装

领域语料、行业连接器、行业验收标准。同样的通用内核，加装不同就成了不同的产品。

法律、医疗的开源项目普遍停在千星级：不是技术不行，是数据拿不到、责任担不起——这两条路的门槛在合规，不在代码。

05
星数不等于健康度

AutoGen 星数仍高于 CrewAI，却已进入维护模式；n8n 是 fair-code 不是 OSI 开源；DeepSeek Harness 是 preview，还出过沙箱逃逸。

只看三样东西：上一次提交是什么时候、issue 有没有人回、谁在为它负责。

三讲到这里收齐了。第一讲看一个 Agent 内部长什么样，第二讲看这些零件怎么连，这一讲看货架上已经摆了什么。第二天从第四讲开始收成一条线：先把 Supervisor 的编排落地，再把这两天的判断写成一页 ADR——那时你手里有结构、有名字、也有理由。
先判档位，再比功能；先问「谁来装、谁来改」，再看「谁星多」。
