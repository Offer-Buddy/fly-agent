1选型不是选最强P0

技术选型最常见的失败不是选了个差的东西，是选了个「很好但团队驾驭不了」的东西。所以先立五条判据，后面每一层都拿这五条去量。

先说清这件事的形状：能力强不强，和你能不能兜住它，是两个独立的轴。

判据问法不合格的表现
可控模型的自由发挥被框在什么范围内没法解释它为什么这么答
可查出了问题能不能还原到具体哪一步只有一句「答错了」，没有链路追踪
可恢复进程被杀、模型超时，能不能接着跑每次失败都从第一步重来
可迁移换框架、换模型要重写多少工具和提示词跟框架绑死
可承担成本、延迟、运维人力是否在预算内上线第一个月账单超预期五倍
一个好选型的标志，是你能用一句话说出「为什么不是另一个」。说不出来，就说明这个决定是抄来的，不是想明白的。
好选型的标志是能说出「为什么不是另一个」；说不出来，就说明这个决定是抄的。

2模型层与编排层P0

模型层：三种接入方式

方式优势代价判据
直连官方接口能力最新、文档最全、问题好排查每家一套 SDK，换模型要改代码只用一个模型、追求最新能力
兼容协议聚合一套协议接多家；换模型只改配置；天然支持降级链多一层中转，极端情况有额外延迟要多家互备、要灵活切换
本地部署数据不出内网、可离线、成本可预测要显卡、要运维、小模型能力有限数据合规硬约束、或高频低成本场景

不管选哪种，降级链和超时预算必须有。这是模型层唯一不能省的东西——它决定了别人家模型抖动的时候，你的服务是慢一点还是全挂。

编排层：三选一

方案什么时候选什么时候别选
图编排框架流程有分支回退、要断点续跑、要做中心调度、要审计只有一个固定三步流程——你只需要一条链
厂商 SDK已锁定某家模型生态，任务偏 coding 或工具调用密集未来要换模型、要跨云部署
自研循环流程极简、团队工程能力强、不想背框架升级债要做持久化、人工介入、多智能体——这些自己写要几个月

如果已经确定要做 Supervisor，编排层的选择其实被反向决定了：多智能体需要中心调度（图天然表达）、需要断点恢复（检查点）、需要审计（每步可见）。这三条换成厂商 SDK 都要自己补，所以图编排是省事的那个选项。

模型层唯一不能省的是降级链与超时预算；编排层怎么选，先看你需不需要「断点续跑」。

3状态层与工具层P0

状态层：存哪、存什么

方案适合不适合典型陷阱
进程内存本地开发、单次请求的临时状态任何要上线的场景发了版才发现状态全丢
缓存中间件会话缓存、短期状态、要极致读写速度需要长期审计、需要事务一致性把缓存当数据库，清了就断档
关系库 + 检查点表要断点续跑、要审计、要按会话回放极高并发下写入压力大只存消息不存流程位置，续跑时不知道下一步

判断标准很直接：要求「杀掉进程还能接着跑」的，只能用持久化存储。缓存可以加速，但不能兜底。

工具层：三种组织方式

方式特点什么时候选
进程内直连最快、最简单，工具就是几个函数工具少、不跨项目复用、单团队维护
工具协议化工具独立成服务，可跨 Agent、跨框架复用；权限可单独控制工具要被多个应用共用，或需要独立部署与升级
统一 API 网关所有外部调用收口，鉴权、限流、审计在一处做对接大量内部系统，安全合规要求高
别被工具数量骗了：十个工具里九个是只读的，风险很低；剩下那一个写工具，就够让整个项目停工整改。选型时先数写工具，不是数工具总数。
缓存可以加速但不能兜底；工具先数「写工具」有几个，不是数总数。

4记忆层与知识层P0

记忆层：存多少，怎么忘

方案能力代价别用在
只做滑动窗口最近若干轮对话，实现成本最低早期信息直接丢失需要跨天、跨会话记住用户
窗口 + 增量摘要用一段摘要承载早期对话，成本可控摘要会丢细节，且摘要本身可能失真需要精确回溯某句话的场景
长期语义记忆把事实抽成条目存向量库，按需检索抽取有延迟和成本；检索可能召回噪音数据量小、个性化收益不明显时
结构化用户画像稳定偏好、身份信息，可直接注入提示词要设计字段，扩展性差快速变化的临时状态

记忆层的真正难点不是「怎么存」，是「什么时候该忘」。存了过期偏好、错误结论、一次性的情绪表达，比不存更糟——它会持续污染后续判断。所以选型时必须一起定：淘汰策略是什么、冲突时以谁为准。

知识层：只做向量是不够的

检索方式强在弱在
纯向量检索语义相近的表述能召回，不怕换个说法精确编号、型号、条款号经常查不准
关键词检索专有名词、编号、代码类查询非常准换个说法就找不到
混合检索 + 重排两边的长处都拿到，靠重排把最相关的顶上来实现复杂，多一次模型调用，延迟上升

判断要不要上重排，看一个指标：提问里有多少是「精确查找」。条款、编号、型号占比高的场景，混合检索不是加分项，是必须项。

记忆的难点是会忘，知识的难点是精确检索——这两层的坑都在「多存一点总没错」的直觉里。

5可观测层与交付层P1

可观测：三个层次，别只做第一层

层次能看到什么解决什么问题
日志发生了什么事件、什么时候、哪个用户知道「出事了」
链路追踪一次请求的完整调用树、每步输入输出、耗时与花费知道「哪一步出的事」
评测固定题集上的得分变化、分类退步情况知道「这次改动是变好还是变坏」

三者缺一不可。只有日志，你查不到根因；只有追踪，你说不清整体质量；都没有，你只能靠用户的抱怨来发现问题。

选型上要考虑一个现实问题：能不能私有化。涉及敏感数据的项目，追踪平台必须能自己部署，否则等于把用户对话又发出去一遍。

交付：从「能跑」到「能交出去」

阶段标志还缺什么
本地能跑自己电脑上能对话环境依赖、密钥管理
单机能起一条命令启动，含数据库认证、限流、监控
可交付别人能装、能重启、能看日志、能限流多副本、灰度、容灾
可运营有成本看板、有质量看板、有回滚方案—

多数项目卡在「单机能起」。判断能不能进下一阶段，只问一句：这套东西能不能交给一个不懂代码的同事，让他自己启动和排查。

日志知道出事了，追踪知道哪一步，评测知道变好没有；三个只有一个，等于没有。

6ADR：把决策写成卡片P1

ADR 是架构决策记录。一页纸，记一个决定。它的价值不在于「显得规范」，而在于半年后你还知道自己当初为什么这么选——以及什么时候该重估。

字段写什么反例
决策一句话，动宾结构：用什么做什么「关于记忆层的思考」——这是标题，不是决策
背景什么约束逼出了这个决定：数据量、合规、团队、工期「因为业界都在用」——这是借口，不是背景
备选认真考虑过的另外两到三个方案列一个明显更差的当陪衬
理由为什么是它：拿五条判据去对「性能更好」——好多少，在什么条件下
代价明确承认牺牲了什么「没有缺点」——说明没想清楚
何时重估触发条件：数据量过多少、成本超多少、团队变了「以后再说」——等于永远不会重估
一个副作用：写 ADR 的过程本身就会改掉一些决定。当你被迫把「代价」写下来的时候，很多看起来不错的选择会立刻露馅。
ADR 的价值不在于规范，在于半年后你还知道为什么；写「代价」那一格时，很多决定会自己改掉。

7八张 ADR 与开工清单P0

动手练习

八张卡，每组领四层，写完互相答辩

每张卡六格：决策 / 背景 / 备选 / 理由 / 代价 / 何时重估。答辩时对方只问三个问题：

  • 为什么不是另一个？（听理由，不听功能罗列）
  • 它挂了怎么办？（听降级路径）
  • 什么时候你会换掉它？（听重估条件）

三问答不上来，这张卡退回重写。

开工检查清单

八张 ADR 写完，拿这张清单过一遍。十条里过不了六条，先别开工。

#检查项验收方式
1每一层都能用一句话说出「为什么不是另一个」口头复述
2每层都有降级或兜底路径，不依赖单一外部服务拔掉一个依赖试
3状态已落持久化，杀掉进程后能续跑真的杀一次
4每个写工具都有权限边界，高危动作有人工闸门逐个工具过一遍
5Supervisor 的委派简报有固定结构，含「不许做什么」看一份真实简报
6全局步数预算与重复检测已配置构造一次绕圈
7一次请求能从头到尾还原成一条追踪链随便挑一次真实请求
8有一套不少于二十题的评测集，有基线分数跑一遍
9单次请求与单日成本都有上限，超了会告警看配置
10密钥不在代码里，日志不含敏感原文搜一遍仓库
这十条不是形式主义。每一条都对应一次真实事故：第 3 条对应重启失忆，第 4 条对应误删生产库，第 6 条对应无限绕圈烧钱，第 8 条对应「改完感觉变好了」。
十条检查过不了六条就别开工；每一条背后都对应一次真实事故。
